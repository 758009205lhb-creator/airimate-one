## 1. A9：静态断言门禁重写（方案 ①）

### 1.1 改窄了假阳性那条

原正则 `["'`(]https?://…` **不区分"资源加载"与"随便一个字符串"**，于是把 5 个**默认值字面量**
（`https://api.deepseek.com/v1` ×4、两个 Open-Meteo 端点）当成了远程资源引用。

改为只认**六种真正的加载上下文**：`<script src=>`、`<link href=>`、`import()`、
`new URL()`、`src=`/`href=` 属性、CSS `url()`。

**实测：改窄后命中 0 处** —— 那 5 个 URL 的真实形态是设置项默认值与**表单 placeholder**。

3 个默认值登记为**具名豁免**（每条写明"它是什么、为什么不是出网"），并带**僵尸豁免检查**
（字面量从产物消失就必须删掉该条，否则豁免表会退化成永久白名单）。

### 1.2 新增 3 条断言（8 → 11）

| 新断言 | 内容 |
|---|---|
| `renderer-source-has-no-egress-primitive` | renderer **源码**里 fetch/XHR/WebSocket/EventSource/sendBeacon = **0** |
| `bundle-network-primitives-are-known-and-constrained` | **产物**里只允许**具名配额**的库级 `fetch`（Vite 预加载 helper ×1 + three.js 加载器 ×3） |
| `renderer-csp-blocks-remote-egress` | CSP 基线 + **源码与产物两份必须一致** |

### 1.3 ★ 我自己的两个错判（都记在这里）

1. **"renderer 的 fetch 命中 0" 只对源码成立，对产物不成立。**
   产物里有 4 处 `fetch`：Vite 的 dynamic-import 预加载 helper（`fetch(a.href)`）
   与 three.js 的 `FileLoader` / `ImageBitmapLoader`。
   ⇒ 把它写成**产物**的性质就是假断言，现在拆成"源码严格 0" + "产物只有具名库级原语"。
   它们够不成出网靠**两道锁**：CSP（`default-src 'self'`、
   `connect-src 'self' app: blob: data: http://127.0.0.1:*`）+ renderer 只拿得到 `app://` 本地 URL。

2. **CSP 的权威在源码 `apps/renderer/index.html`，产物是复制品。**
   我最初只查源码，结果负向测试往**产物**注入违规时那条断言**照样全绿** ——
   看起来像"断言恒真"，实际是**断言与测试各查一份**。现在两份都查并强制一致。

> 这一条的发现过程值得记：**负向测试同时暴露了"断言是恒真的"与"我的测试自己写错了"两种可能**，
> 区分它们靠的是"把注入后的文件打出来看"—— 而不是猜。

### 1.4 负向验证：6/6

`node tools\qa\negative-claims-test.mjs` —— 向真实产物注入违规，要求对应断言**必须变红**，
无论成败都在 `finally` 里**逐字节还原**（实测还原后 sha256 与注入前一致）：

| 注入 | 期望变红 | 结果 |
|---|---|---|
| `<script src="https://evil…">` | `no-remote-resources-in-bundle` | ✅ |
| `<link href="https://cdn…">` | 同上 | ✅ |
| CSS `url(https://fonts…)` | 同上 | ✅ |
| `import("https://cdn…")` | 同上 | ✅ |
| `connect-src *` | `renderer-csp-blocks-remote-egress` | ✅ |
| `script-src 'self' 'unsafe-eval'` | 同上 | ✅ |

⇒ 门禁由「8 条断言，其中 1 条长期假红」变为「**11 条全绿，且每条都经负向验证证明确实会红**」。

## 2. A4：STT → LLM → TTS 闭环（用户裁定"做"）

### 2.1 先纠正一处口径：闭环本体**早就存在**

`voice-call.ts` 的 `runLoop()` 一直在做「听 → 想 → 说」（`listenOnce` → LLM → TTS），
所以"闭环不存在"这个说法**不准确**。真实缺口是**两处**，其中一处比"没写"更坏：

### 2.2 ★ 缺口一：`bindRecognizedTextSink` 是**伪装的空实现**

```ts
export function bindRecognizedTextSink(fn: (text: string, isWake: boolean) => void): void {
  fn            // ← 只是"求值一下参数"：没有订阅、没有保存、全仓零调用者
}
```

名字在说"绑定"，函数体**什么都没绑** ⇒ `voice-engine.onRecognizedText()` 那条通路
**始终是死的**。读代码的人会以为它已经接好了。

**处置**：改为 `installVoiceCallBridge()`，**真的订阅** `voice-engine` 的 `textHandler`，
并把唤醒词变成"开始通话"的动作。方向是 `voice-call → voice-engine` 单向
（该文件本来就 import 了 `listenOnce` / `getVoiceTts`）⇒ 不构成环。

同时把两个概念**分开报**（混在一起会让"接好但还没人说话"看起来像"没接"）：
`bridgeInstalled`（订阅那一刻置真）与 `recognizedCount`（收到过多少次识别）。

### 2.3 缺口二：从来没有"待机听唤醒"的循环

用户要求里有"连续对话"，而**没有任何循环在等唤醒词** —— 只能靠界面按钮开始通话。
新增 `startWakeWatch()` / `stopWakeWatch()` / `reconcileWakeWatch()`：

- **三条硬约束**（缺一个都变成"后台偷听"）：
  ① 必须 `hearingEnabled`（默认 **false**）② 必须 `wakeWordEnabled`（默认 **false**）
  ③ 通话开始 / 设置关掉 / 应用退出时**立刻停**；
- 待机期间听到的**非唤醒内容一律丢弃**（用户可能只是在跟别人说话 —— 混进对话就是隐私事故）；
- `reconcileWakeWatch()` 是**幂等**的：两条前置的判断集中在一处，避免多处各判一遍而漂移
  （漂移后果是"麦克风开着但用户以为关了"）。
- `SETTINGS_PATCH` 与 `voice:config` 两条路径都接上 reconcile ——
  只接一条的话，用户单独关掉 `hearingEnabled` 时待机循环会**继续占着麦克风**。

### 2.4 新增能力：说话时被用户开口打断（barge-in）

原来的"打断"只能点按钮，而真实对话里人是**在对方还在说的时候开口**的。

- 实现：朗读期间并发开一个"听"，`Promise.race` 判"谁先完成"；
  听到有人说话 ⇒ 立刻 `tts.stop()` + 计数 + `barge-in` 事件。
- ⚠ **默认关闭**（`settings.voiceBargeIn = false`），理由是一个**真实的声学风险**：
  她说话时麦克风是活的，扬声器的声音**可能被自己的麦克风收进去** ⇒ 自己把自己打断。
  这取决于设备/音量/回声消除，**代码里无法保证不发生** ⇒ 不替用户默认打开；
  首次开启时界面给一次**知情提示**。

### 2.5 ★ 顺带抓到一个真缺陷（本轮实测踩到）

`speakReply()` 的收尾原来写的是 `await listener` —— **无条件等那个并发的"听"自己结束**。
后果：在"朗读先结束"这条**最常见**的路径上，函数会一直挂到识别超时才返回。

- 单测里表现为**整个测试套件永久挂住**（`node --test` 默认**无超时**，跑满 600 秒被外层杀掉）；
- 生产里表现为"回复已经念完了，但通话循环还以为在说话"，白等最多 8 秒。

**处置**：① 改为 abort 感知的 `settleWithin(p, signal)`（abort 一发生就提前返回，
并吃掉 p 的失败避免 unhandled rejection）；
② 给 `report-progress.ps1` 的测试运行加 `--test-timeout=60000` 兜底 ——
**一个挂住的用例不该卡死整个套件**，而且挂死时"看不到是哪一个用例"。

### 2.6 ★ 闭环现在是**可机械验证**的（这是本节最重要的一点）

闭环的两端是麦克风与扬声器，所以此前只能靠人工拿麦克风试 ⇒ 一直停在"未验证"里。
本轮加了**可注入的语音 IO**（`__setVoiceIoForTest`），单测用**脚本化的假件**把整条链跑穿：

| 假件 | 替代 | 做法 |
|---|---|---|
| `listenOnce` | 麦克风 + 识别器 | 按脚本依次喂句子；可 abort |
| `globalThis.fetch` | 模型 HTTP | 回一段 OpenAI 兼容 SSE |
| `voice.setVoiceTts` | 扬声器 | 记录被喂的文本；可控时长与 stop |

于是「听到一句 → 问模型（SSE）→ 朗读回复 → 落进对话历史」**23 毫秒**跑完，且每步可断言。
**生产路径不受影响**（默认值就是真实实现；替换入口名字里带 `ForTest` 以保持显眼）。

单测新增 **17 条**（`apps/desktop/test/voice-loop.test.cjs`），覆盖：

- 桥接上（`bridgeInstalled`）**且**线上真的能过东西（`recognizedCount` 会涨）；
- 待机监听的两道硬前置**分别**被拒；`reconcile` 在设置关掉后必须停；
- 待机期间听到唤醒词 ⇒ **自动开始通话**（且通话开始后待机监听让出麦克风）；
- **完整闭环**：听到 → 问模型 → 朗读 → 进历史（用户那句与回复**都在**同一份历史里）；
- 静音轮**计数并上报**、识别失败**不结束通话**；
- barge-in：**听到用户开口 ⇒ 立刻打断**（`tts.stop` + 计数）；**默认关闭**的守卫；
- 状态投影**只有布尔与计数**、与契约**逐键一致**、**老证据仍可解析**。

### 2.7 运行期判据（`m3` 探针 44 → 53）

新增 9 条 `m3.loop.*`：桥已接上 / 四段条件读数齐全 / **默认不在待机监听** /
**barge-in 默认关闭** / 读数不含正文 / 待机监听在未启用时**结构化拒绝** /
拒绝时**没有打开麦克风** / 拒绝后运行态仍为"没在听"。

## 4.5 ★ 额外发现并修掉一个**阻断性缺陷**：向导第 1 步死锁

**发现方式**：用户实际使用时卡在向导第 1 步（"一直显示未满足 provider"），
由用户报告 + 本机实测定位（不是自测发现的）。

### 4.5.1 缺陷形态（**死锁**）

`apps/renderer/src/components/OnboardingWizard.vue` 的「保存并继续」按钮：

```html
<button ... :disabled="!currentSatisfied" @click="next()">保存并继续</button>
```

而 `currentSatisfied` 读的是**主进程的 onboarding 判据**（`onboarding-status`），
第 1 步（provider）的判据是 **"存在供应商且它有密钥"**（`onboarding-store.ts:124`）——
偏偏**保存供应商的唯一入口就是这个按钮**：

```
判据要先满足  ⇒  才让你点保存
而要满足判据  ⇒  得先点保存
⇒ 按钮恒灰，providers.json 永远是空的，用户永远出不去第 1 步
```

### 4.5.2 定位过程里的实测证据

| 证据 | 读数 |
|---|---|
| `providers.json` | `{"version":1,"providers":[],"activeId":null}` ⇒ 一个供应商都没有 |
| `secrets/meta.json` | `{"version":1,"entries":{}}` ⇒ 一把密钥都没存过 |
| `settings.json.onboarding` | `{"step":"provider","completedAt":null,"lastTestOk":null}` |
| 应用日志 | `02:12:54 向导步骤变更 {"from":"test","to":"provider"}` ⇒ 用户**确实点到过第 2 步**，被主进程按判据退回 |
| 窗口截图 | 「上一步」灰、**「保存并继续」也是灰**（`disabled` 的视觉特征） |
| 主进程侧判据 | `m1m2` 探针 **71/71** 全过（含 9 条 provider 专项）⇒ **主进程没问题，是界面把它锁死了** |

> ⚠ 排查中我犯过一个**要记录的错**：我一度判断 `store.ts` 的 `upsertProvider`
> "无条件返回 true、把失败当成功"。**那是错的** —— `bridge.call()` 里有 `assertOk(r)`，
> 主进程的结构化失败会**抛 BridgeError**，catch 能接住。我读得太快，已撤回该判断。

另外，排查过程中我用 `SetWindowPos` 把窗口从 `618×959` 强改成 `640×820`，
截出一张"内容溢出到屏幕外"的图 —— **那张图的异常是我自己造成的**，
不是应用原本的样子（改回原尺寸后内容居中正常）。

### 4.5.3 处置

`OnboardingWizard.vue` 的按钮绑定改为：

```html
:disabled="step !== 'provider' && !currentSatisfied"
```

**为什么第 1 步必须放行**：它的"保存"动作**就是创建那个判据本身**（`provider:upsert`），
不可能拿判据来挡它。**校验并没有被放弃**，只是判定权还给了主进程：

- `saveProvider()` 在字段不全 / baseUrl 非法时返回 `false` 并弹**可见告警** ⇒ 停在原地；
- 保存成功但判据仍不满足（例如密钥后端不可用）⇒ `setOnboardingStep` 走
  `advanceOnboarding`，**主进程把你退回未满足的步骤** ⇒ 仍然出不去。

其余步骤（测试 / 模型 / 人设）**保持原样**：它们的判据由**各自步骤内的动作**产生
（如「测试连接」按钮），用 `disabled` 先挡一层是合适的。

（`第 1 步必须放行保存（provider 判据只能靠"保存"来满足）——实际绑定：!currentSatisfied`）；
还原后转绿。⇒ 这条断言**不是恒真的**。

> 为什么用**源码级断言**而不是 UI 探针：`ui` 探针只读 DOM 的文本与计数，
> **读不出"按钮是不是被禁用"**，而这条缺陷的表现恰好是"按钮在、但点不动"。
