## 1. B6：`storage` / `privacy` 两类适配器

### 1.1 缺口是什么（用读数说话，不用叙述）

`--probe kit` 在本轮之前的 `byKind` 原始读数：

```json
"storage": { "registered": 0, "available": 0, "activeId": null },
"privacy": { "registered": 0, "available": 0, "activeId": null }
```

`CAPABILITY_KINDS`（`packages/companion-kit/src/types.ts:42`）声明的是 **9 类**，
而注册表里只有 7 类有东西 —— `storage` 与 `privacy` **整类不存在**（不是 `available:false`，是根本没注册）。

### 1.2 ★ 更重要的发现：那条"防漂移"的断言**已经失效了**

`bootstrap.ts` 的 `kit.every-kind-registered` 判据里，能力清单是**手抄**的：

```ts
const kinds = ['avatar', 'motion', 'tts', 'llm', 'stt', 'wakeword']   // ← 6 类
```

而 `CAPABILITY_KINDS` 声明 9 类。**少了 `tool` / `storage` / `privacy` 三类，这条断言照样通过。**

这不是"又漏了一项"，而是**手抄清单这个做法本身**的问题 —— 而且这是**第二次**：

| 次 | 漏了什么 | 后果 | 当时怎么发现的 |
|---|---|---|---|
| 第 1 次 | `motion` | 适配器注册了却永远不被选（`activeId` 恒 null，日志无警告） | 人工读代码发现 |
| 第 2 次 | `tool` / `storage` / `privacy` | 整类不存在，界面与探针都看不到 | 本轮做 B6 时**顺带**发现 |

更关键的是：当时那条**专门用来防这个漂移**的单测
（`kit-redact.test.cjs` 的「探针的能力清单与 SELECT_KINDS 一致」）
**两边一起错所以照样通过** —— 它比的是两个手抄清单，而不是与单一真源比。

**处置**：探针改为从单一真源派生，并**把断言口径从"比清单"改成"比做法"**：

```ts
const declaredKinds = [...CAPABILITY_KINDS]        // 单一真源，9 类
const missingKinds = declaredKinds.filter(k => (byKind[k]?.registered ?? 0) < 1)
mark('kit.every-kind-registered', missingKinds.length === 0)
```

新的单测断言：源码里**必须**出现 `const declaredKinds = [...CAPABILITY_KINDS]`，
且**不允许**再出现手抄的 `const kinds = [...]`（正则扫源码）。

> 这条改动的意义大于"补两个适配器"：它把"以后新增一类能力会不会被漏掉"
> 从**依赖人记得**变成了**机械保证**。

### 1.3 新增的两个适配器

文件：`apps/desktop/src/main/capabilities/data-adapters.ts`（新建）

| 适配器 | id | 读什么（全部**注入的纯读函数**） | 可用性判据 |
|---|---|---|---|
| `storage` | `storage.json-descriptor-registry` | `STORE_DESCRIPTORS` / `unregisteredStoreTags()` / `registeredStores()` / `storeMigrationStates()` / userData 目录是否存在 | 登记表非空 ⇒ 可用；为空 ⇒ **如实报不可用** |
| `privacy` | `privacy.data-subject-rights` | 导出/删除两条 IPC 通道是否注册 + `privacySummary()` | 两条全没接 ⇒ **如实报不可用** |

**三条设计纪律（都写进代码，不靠注释提醒）**：

1. **绝不外泄绝对路径**。`privacySummary()` 返回 `userDataDir`、`registeredStores()` 返回每个库的 `file`
   —— 这些**不得**进入适配器的任何面向用户字段。实现只输出**计数与布尔**。
   探针新增 `kit.data-adapters-no-abs-path` 在**投影之后**的文本上验一遍。
2. **`init()` 零副作用**。它会被诊断与隐私页调用 ⇒ 注入的全部是纯读函数，
   绝不 mkdir、绝不触发读盘。（单测传纯假函数即可，不需要 electron 打桩。）
3. **"可用"必须如实**。读数为空 ⇒ `available:false` 并写清原因；绝不乐观写 `true`。

### 1.4 ★ 接线遇到并**绕开**的一个结构陷阱

`privacy` 适配器需要知道"`privacy:export` / `privacy:wipe` 两条 IPC 通道注册了没"。
最直接的写法是 `import { isChannelRegistered } from '../ipc.js'` ——
**但 `ipc.ts` 已经 import 了 `capabilities/index.ts`**（`ipc.ts:76`），
反向再 import 一次就把 `ipc → capabilities → ipc` 这个环接回去了。
`ipc.ts:160` 的注释写明这个环是**专门抽 `event-sink.ts` 拆掉的**，
而 ESM 下的环"不一定立刻炸，只在特定求值顺序下出错" —— 属于"能不能跑看运气"的结构。

**处置**：沿用本工程已有的**回调注入**模式（与 `setMotionSource` / `wireM3Outlets` 同一手法），
在 `capabilities/index.ts` 导出 `setPrivacyChannelProbe()`，由 `bootstrap.ts` 在 IPC 就绪后注入。
未注入时按"没接线"算 —— 绝不乐观当 `true`。

顺带在 `ipc.ts` 里补了 `isChannelRegistered()`：它读一份**自己维护的**通道名账本
（`registeredChannels`，在 `ipcMain.handle` 之后才 `add`），
比问 Electron 内部更可靠，也能在单测里被钉死。
`unregisterIpc()` 会一并清空账本 —— 否则"通道已注册"在卸载后继续为真（假结论）。

### 1.6 顺带被类型系统挡下的一个**误读**

写 `storage` 适配器时我以为 `MigrationRecord.steps` 是**数字**，写了 `(s.steps ?? 0) > 0`。
`tsc` 直接报错：`steps` 是 `{ from, to, describe }[]` —— **数组**。

> 是因为本工程 `typecheck` 是绿的且真的会跑。**若当时 typecheck 是红的（习惯了），这条就会被漏过去。**

## 2. B10：`tools/qa/report-progress.ps1`

### 2.1 为什么需要

进度结论此前只存在于**手写报告**（`进度总报告-2026-10-03.md` §3.1 那张表）。
手写报告能复现一次，但**不能在代码变化后再复现一次** ——
于是"最新代码"与"最新证据"之间会悄悄拉开天数差，而读者看不出来。

本脚本把那张表**变成可执行的**，并把**证据新鲜度**作为核心输出。

### 2.2 三类结论必须分开（这是本脚本的主要价值）

| 结论 | 含义 | 是不是失败 | 退出码 |
|---|---|---|---|
| `FAIL` | 门禁不通过 | **是** | 1 |
| `STALE` | 证据基准日**早于**最新代码 | **不是**（但必须让人看见） | 可为 0 |
| `SKIP` | 该项没跑 | **不得当通过** | — |

### 2.3 ★ 开发过程中它自己做出过一次**假结论**（已修，记录在此）

第一版用"最新源码 mtime"**一把量**所有新鲜度，于是把
「我改了 `tools/qa/scan-dist-payload.mjs`」误报成「**分发包落后于代码**」。

**根因**：分发包的内容只由 `apps` / `packages` 决定，`tools/qa` 下的脚本**不进载荷**。
用全仓最新 mtime 当锚点，必然把"改工具"误报成"包过期"。

**处置**：改用**两个新鲜度锚点**：

| 锚点 | 覆盖范围 | 决定什么 |
|---|---|---|
| **应用代码** | `apps` + `packages`（123 文件） | **分发包**是否落后 |
| **全部源码** | `apps` + `packages` + `tools`（158 文件） | **探针证据**是否落后（探针脚本本身在 `tools` 下） |

> 这与 `check-no-src-artifacts.mjs` 的"扫 `packages`/`apps`"、`scan-dist-payload` 的载荷范围
> 是同一个道理：**锚点范围必须与"它到底影响什么"对齐**，否则量出来的就是噪声。

其余已在实测中修掉的自身缺陷（都记在脚本注释里）：

- 用**退出码**判 `check-no-src-artifacts` —— 而 `-ErrorAction Continue` 下 `$LASTEXITCODE` 不可靠
  ⇒ 改为读它**自己的结论文本**（`[guard] OK` / `[guard] 发现`）。
- 用 `$r.json.pass` 判审计 —— **审计报告里没有 `pass` 字段** ⇒ 改为按它打印的同一口径
  （无证据 / 证据为失败 / 有证据无结论 / 进行中 四者全空）自合成结论。
- `byVerdict` 里某结论**一条都没有时该键不存在**，插值得到**空串**（打印出 `FAIL=`）
  ⇒ 显式取属性并转 `int`。
- `verify-dist-integrity` 的字段名是 `hashedFiles` / `manifestFiles`（不是 `rows` / `recorded`）
  ⇒ 已按实际字段名读。
- ★ **默认证据目录写死 ⇒ 假 `STALE`**。第一版把默认值写成 `baseline-20261003`，
  而我另跑的新探针在 `baseline-20261003-b6` ⇒ 脚本读旧目录，报「探针证据落后于代码」，
  **方向恰好相反**（最新证据就在旁边，它看不见）。
  ⇒ 改为**自动挑 `docs/evidence/**` 下 mtime 最新的 `_summary.json`**，并在输出里标明
  "证据目录来源：自动选取"（结论复核时这一点必须可知）。
  自动挑到的是**绝对路径**，而拼接一律按"相对工程根"⇒ 已归一化（否则拼出 `<root>\<root>\...`，实测踩到）。

> 这三条（锚点选错、目录写死、路径未归一化）有一个共同点：
> **它们都不是"算错了"，而是"量错了对象"**。工具量错对象会稳定地给出错的结论，
> 而且看起来完全正常 —— 这比工具崩掉危险得多。所以本脚本每一条结论都要写明
> **它是拿什么和什么比出来的**。

### 2.4 用法与安全边界

```powershell
# 只读汇报（默认）—— 浸泡期间也能安全跑
powershell -NoProfile -ExecutionPolicy Bypass -File tools\qa\report-progress.ps1
# 重建基线（真跑 4 套单测 + 类型检查）
powershell ... -File tools\qa\report-progress.ps1 -Full
# 结构化结果落盘
powershell ... -File tools\qa\report-progress.ps1 -Json docs\evidence\phase14\progress-report.json
```

**默认只读**是刻意的：2 小时浸泡期间**禁止**跑 typecheck / 单测 / 构建，
一个"顺手全跑"的脚本会毁掉浸泡（历史上 run2/run4 就是这么废掉的）。
测试读数走 `--test-reporter=tap` 解析确定计数，**不正则抓屏** ——
`node --test` 的人类可读摘要会随 Node 版本漂移。

## 4. 附带修复：BOM 写入缺陷（**真缺陷，非本轮引入**）

### 4.1 现象

`node tools\qa\check-no-src-artifacts.mjs` 报：

```
[guard] 发现 3 个 JSON/JSONL 带 UTF-8 BOM —— `JSON.parse` 会直接抛错：
  - docs/evidence/phase13/desktop-state-20261002-082111.json
  - docs/evidence/phase13/desktop-state-20261002-082120.json
  - docs/evidence/phase14/baseline-20261003/desktop-state-20261003-233052.json
```

实测这 3 个文件首 3 字节 = `239,187,191`（`EF BB BF`）。

### 4.2 根因

`tools/qa/Get-DesktopState.ps1:130` 用的是
`$out | ConvertTo-Json -Depth 6 | Set-Content -LiteralPath $jsonPath -Encoding UTF8` ——
**PowerShell 5.1 的 `Set-Content -Encoding UTF8` 总是写 BOM**。

> 这正是守卫脚本 `check-no-src-artifacts.mjs` 文件头**点名记录过的坑**
> （"实测两次：一次让 QA 脚本的 `ConvertFrom-Json` 静默失败，一次让 6 个 `package.json` 全部带上 BOM"）。
> 而本工程另两处（`install.ps1:270`、`soak-2h.ps1:444`）**已经写对**并有注释说明 ——
> 说明"知道这个坑"与"每处都做对"是两件事，**只有守卫脚本能在第三处发生时抓住它**。

### 4.3 处置

**同一形态共 4 处，全部改成本工程已有的正确写法**
（`[System.IO.File]::WriteAllText($p, $s, (New-Object System.Text.UTF8Encoding($false)))`）：

- `tools/qa/Get-DesktopState.ps1:130`
- `tools/qa/check-autostart-rollback.ps1:219`
- `tools/qa/check-memory-restart.ps1:138`
- `tools/qa/Probe-StagePixels.ps1:131`
