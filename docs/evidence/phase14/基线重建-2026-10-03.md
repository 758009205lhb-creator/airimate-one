### 3.1 ⚠ 汇总口径上的一个真陷阱（本轮踩到并修掉）

**不能靠 `pass` 字段数数。** 各探针的判定字段命名并不统一：
`pass` / `allPass` / `passA10` / `passHitRegionMatchesVisual` / `passWheelInWindow` / `checks{…}` 都有。
第一次汇总得到 `checks=0/0` —— 那是**假空结果**，而"假空"与"真失败"无法区分。

因此新增 `tools/qa/summarize-probes.mjs`，它**递归收集一切 `pass*` 布尔 + `checks{…}` 计数**，
并显式**不把 `ok` 当判定字段**：本项目大量使用「**拒绝即正确**」的语义 ——
`listenWhenDisabled.ok=false`、`callStartDenied.ok=false`、`fsAddSensitive.ok=false`、`badUrlReject.ok=false`
全都是**门禁正确工作**的读数；把它们当失败会得到**完全相反**的结论（第二轮汇总就这么错过一次）。
同理 `errors:[0]` 表示"0 个错误"，不是"有 1 个错误"。

> 这两处都是**测量工具的缺陷**，不是应用缺陷。修好之后才是 11/11。

### 3.2 汇总器还要能识别"**这个文件不是探针**"（本轮又踩一次）

同一目录里还有 `desktop-state-2026…json`（桌面/窗口清点快照）——它**没有 `pass*` 字段**，
硬判就得到"JSON 解析失败（BOM）"的**假失败**。现在按文件名模式跳过，并把跳过的文件**列出来**
（`skippedNonProbes`），避免"少算了却不知道"。

### 3.3 ⚠ 一条**抖动**判据（不是回归，但必须留档）

批量重跑时 `a13`（待机轮换）出现一次 `pass=false`：`switchCount=1 / distinctClipsObserved=2`，
即 **27 s 窗口内只观察到 1 次轮换** —— 而 12 s 轮换本应有 2 次。

- **连跑 3 次复核：`pass=true`，`switchCount=2 / distinct=3`，三次完全一致** ⇒ 判为**时序抖动**。
- 机理：探针从**应用启动**就开始采样，而首轮轮换要等 ~12 s；若启动本身慢，
  窗口内就少看一次切换。**与渲染/动效逻辑无关**（本轮改动只在主进程存储与探针读数路径）。
- 复现命令：`run-probe.ps1 -Name a13`（连跑 3 次即见稳定 PASS）。
- ⚠ **未擅自放宽这条判据**：改它等于改"12 s 轮换"的验收口径，属用户裁定范围。
  若希望根治抖动，正确做法是让探针**等到舞台就绪后再起窗口**，而不是把阈值调松。

## 4. 本轮代码改动（B1：修最后一个"升级可能丢数据"的缺口）

**背景修正**：外部复核在 2026-10-02 抓到的两个缺口，**大部分已被修过**（本轮实测确认）：
`storeName` 已逐字补全、`json-store.ts` 的 `lastMigration` 已改为从注册表实时读、
`settings` / `secrets-meta` 已各自接上迁移链、`session` / `memory` 已走 `createJsonStore`。

**剩下的真缺口只有一个：`apps/desktop/src/main/provider-store.ts`。**

它手写了"原子写 + schema 校验 + 损坏回退"，但**完全没有 `migrateStore()`**：
`providers.json` 一旦升版（schema 是 `version: z.literal(1)`），校验立刻失败 ⇒ 回退**空配置**
⇒ **用户配置过的全部供应商消失**（baseUrl / 模型名要重新填）。这比"少一条记录"严重得多。

**修法**（与 `settings-store.ts` / `secrets-store.ts` 同一套顺序）：

1. **先认旧裸数组格式**（早期 `providers.json` 就是 `Provider[]`），逐条过 `ProviderSchema`，坏条目丢掉；
2. **再过迁移链** `migrateStore(raw, storeDescriptor('providers'))`；
3. **再归一化版本**后交 schema 校验（schema 只管形状，版本由迁移链掌管）；
4. 迁移不了（版本更新 / 缺步骤 / 抛错）⇒ **保留原文件**、以空配置运行、如实记原因。

**★ 这次修复自己踩到一个第二层缺陷（值得留档）**：
`migrateStore()` 对"没有 version 字段"的输入在目标版本为 1 时返回 `ok:true` 且**原样透传** ——
它只保证"版本可接受"，**不保证形状是对象**。于是裸数组会一路走到 `StoreSchema` 才失败，
**回退空配置**，也就是"我修了迁移，却仍然丢数据"。
新增的用例 `供应商配置：旧裸数组格式必须仍能读出来` **先红后绿**才把这条抓出来 —— 这正是"光测库不测接线等于没测"的又一例。

**新增 3 条用例**（`apps/desktop/test/store-migration.test.cjs`，15/15）：
① 版本比程序新 ⇒ 拒绝读 + **保留原文件** + 以空配置运行；
② 登记名可查、迁移结论可读（不是永远 null 的摆设）；
③ **旧裸数组格式仍能读出来** + 写盘升级为带 `version` 的新格式。

## 4.1 收尾轮补充（同日稍后）：`kit:stores` 的接线被真正验证了

B1 修的是"迁移链接没接上"，但**没有一条判据验证过"迁移结论能不能被界面看到"**。补测时抓到两件事：

**① 三个手写存储根本没进登记表（真缺口，已修）**

`settings` / `providers` / `secrets-meta` 因为各自的原因（防抖落盘、兼容旧裸数组、密钥目录）
**手写**了原子写与校验，它们各自**接了 `migrateStore()`**，但**从未登记** ⇒
`kit:stores` / 隐私页 / 诊断里**整个看不到这三个存储**（不是显示 null，是根本不在）。
而登记表存在的唯一理由，就是让界面能区分 "**没登记**" 与 "**登记了但没迁移**" ——
少了这三个，那个区分偏偏对**最该被看见**的设置、供应商配置、密钥元数据失效。

修法：新增 `registerMigrationProbe(storeName, tag, probe)`（**纯读**探针，不触发读盘/写盘），
三个存储各自登记一条。同时把登记项的类型从 `store: JsonStore` 收紧成最小接口 ——
顺带修掉一个运行期隐患：`registeredStores()` 会对只装了探针的条目调 `file.storePath()` ⇒ 炸。

**② 登记表的"重置"语义错了（已修）**

单测的 `beforeEach` 调 `__resetStoreRegistryForTest()`，而它原来是 `registry.clear()` ——
于是那三个**在模块顶层登记**的常驻条目被永久清掉，表现为"三个存储不见了"的**假失败**。
现在"重置"= **回到种子状态**（模块加载完成时的登记集合），不是清空。

**③ 探针把最关键的两个输出丢掉了（已补两条判据）**

旧版 `kit` 探针只读 `name/version/description`，然后把整个 `kitStores()` 响应丢掉，
于是"登记表接线"被验证成了"清单数量对不对"。现补：

| 新判据 | 含义 |
|---|---|
| `kit.stores-migration-readable` | **每个**存储条目都带 `lastMigration` 键（含 `null`）⇒ 响应没被清洗掉、界面真能区分"没登记/没迁移" |
| `kit.stores-none-unregistered` | `unregistered` 为空 ⇒ 没有被悄悄跳过迁移链的存储 |

**活体读数**（`kit.json`，39/39 PASS）：

```
count = 13            lastMigrationFieldCount = 13
outcomes（有读盘结论）= 12 条
migratedNames（真的走过迁移步骤）= []      ← 与"当前全是 v1"一致
unregistered = []                          ← 没有被跳过的存储
```

> ⚠ **语义陷阱（我本轮差点因此得出相反结论，留档）**：
> `lastMigration` 是**上次读盘的迁移结论**，**不是"发生过迁移"的事件**。
> v1 数据 + v1 描述子时它照样是 `{ok:true, steps:[], reason:'ok', fromVersion:1}` —— **不是 null**。
> `null` 只出现在"已登记但还没读盘"（如本次的 `knowledge-cache`：探针没触发它读盘）
> 或"未登记"（那种情况键根本不存在）。**把非 null 一律读成"迁移过"是错的。**
> 探针因此把 `outcomes` 与 `migratedNames` **分成两栏**记录。

**④ 顺带纠正一条我自己的错误读数**：`kit.json` 的 `stores.count` 是 **13**，不是 0 ——
先前用 PowerShell 点取嵌套属性时读错了，后改用 Node 复核才看清。**工具读错与数据错要分清。**
