# A18 · 端口审计（通过）

| 字段 | 值 |
|---|---|
| 判据 | **A18**：非环回监听端口 = 0（或所有必要端口都满足随机端口 + 环回 + 一次性鉴权） |
| 命令 | `Get-NetTCPConnection -State Listen`（只读） |
| 结果 | **PASS** —— 本应用**没有任何监听端口** |

## 原始输出

```
本机监听项总数=33            本应用进程数=0
本应用监听项=0
非环回监听项（全机）=19
无法归属到进程的监听项=2
PASS: 本应用监听端口 = 0
```

## 判定

| 检查 | 要求 | 实测 | 结论 |
|---|---|---|---|
| 本应用监听端口 | 0（首选） | **0** | ✅ |
| 本应用是否有非环回监听 | 不得有 | 无（因为压根没有监听） | ✅ |
| 样本有效性 | 必须真的查到了监听项 | 全机 33 项 | ✅ 不是"查了个空" |

## 两点必须说明的口径（避免"假通过"或"假失败"）

1. **全机 19 项非环回监听与本应用无关**：它们属于**其它软件**（例如本机 `127.0.0.1:7890` 的代理
   及其 `::` 监听项）。判据只能针对**本应用进程**断言 —— 这也是 `Acceptance-Matrix` 里
   把口径定成"本应用相关 socket"的原因。若强行断言"全机非环回 = 0"，
   会把用户自己的软件判成我们的失败，那是错的判据。
2. **"无法归属到进程的监听项 = 2"**：Windows 上这两个是已知的系统保留 socket（PID 0/4），
   与我们的进程无关。我们**不去杀、不去改**任何别人的监听项。

## 设计侧的依据（为什么天然是 0）

本应用**不需要任何监听端口**：
- LLM/TTS 出网请求全部由**主进程**发起（`fetch` 出站，不监听）；
- renderer 与主进程走 Electron IPC，不需要本地 socket；
- 资源加载走自定义协议 `app://`（`protocol.handle`），不走 HTTP 服务；
- 诊断导出走 `--diagnostics <file>` / `--probe-out <file>` **写文件**，不新开端口。

⇒ "只用随机端口 + 环回 + 一次性 token"那条退路在本版本**未被使用**。
若将来引入本地 TTS 桥，必须在该模块内实现这三条约束并在本判据下重新验证。
