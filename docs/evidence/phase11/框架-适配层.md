## 3. 许可闸门

### 3.1 `judgeLicense()` 的三档语义（`types.ts:126-166`，**唯一实现**）

原文（`types.ts:137-166`，逐字）：

```ts
export function judgeLicense(lic: AssetLicense, profile: RuntimeProfile, requireCommercial = false): LicenseVerdict {
  if (profile === 'development') {
    return { allowed: true, reason: 'ok-development-private', detail: '开发形态：允许本机使用任意来源资产（不得随分发给出）' }
  }
  if (lic.provenance === 'licensed') {
    if (requireCommercial && !lic.commercialUse) {
      return { allowed: false, reason: 'denied-commercial-without-commercial-right', detail: `资产「${lic.license}」未授予商用权利` }
    }
    return { allowed: true, reason: 'ok-licensed', detail: `许可：${lic.license}` }
  }
  if (lic.provenance === 'builtin-fallback') { return { allowed: true, reason: 'ok-builtin-fallback', detail: '内置占位资产（自研，可再分发）' } }
  if (lic.provenance === 'user-provided')   { return { allowed: true, reason: 'ok-user-provided',   detail: '用户自备资产（仅在本机加载，不随包分发）' } }
  if (lic.provenance === 'unknown') {
    return { allowed: false, reason: 'denied-packaged-unknown-license',
             detail: '资产许可未知 ⇒ 分发形态下拒绝加载（请替换为许可明确的资产）' }
  }
  return { allowed: false, reason: 'denied-packaged-non-redistributable',
           detail: `资产为私有来源（${lic.license}），禁止进入分发载荷；商业版必须替换` }
}
```

三档归纳：

| 档 | 条件 | 结果 |
|---|---|---|
| ① | 运行形态 = `development` | **允许任何来源**（含 `private-only` / `unknown`）。**本构建就是这一档**（私有自用） |
| ② | 形态 = `packaged` 且 `requireCommercial === true` | 来源必须 `licensed` **且** `commercialUse: true`；否则 `denied-commercial-without-commercial-right` |
| ③ | 形态 = `packaged` 且不要求商用 | 来源必须是 `licensed` / `builtin-fallback` / `user-provided`；`private-only` ⇒ `denied-packaged-non-redistributable`，`unknown` ⇒ `denied-packaged-unknown-license` |

**把话说白：** `development` 允许私有资产 —— 这是**私有自用构建的正常形态**，不是"给私有资产开后门"；
`packaged` 则**机械地**拒绝一切非再分发来源，**并且额外拒绝一切"来源不明"**（`unknown` 不给"猜一猜"的余地）。

这个顺序**有两个消费方**，不是一张说明表：
① `resolveAvatars()` 用它排序 —— "许可越宽松越优先"（`asset-resolver.ts:174-178`），

② `kit.test.mjs` 的 `★ unknown 必须比 private-only 更保守（顺序表的意义）` 直接断言这个不变量。

### 3.3 两种运行形态是怎么判定的

```ts
export function resolveRuntimeProfile(): RuntimeProfile {
  const override = process.env.AIRIMATE_PROFILE
  if (override === 'packaged' || override === 'development') return override
  return process.env.AIRIMATE_WORKSPACE ? 'packaged' : 'development'
}
```

注释（`:46-51`）说明了为什么需要显式覆盖：本项目把 `electron.exe` 改名成 `AiriMateOne.exe`，

```
* 替换后这些格式会**合法出现**在载荷里 —— 但那是**另一个构建**（不同许可、不同资产清单）。
* 保留拦截的意义是：**本源构建绝不允许悄悄混入资产文件**，
* 而合法的商业载荷必须显式改这份清单（改一次 = 一次有意识的许可决策，
* 而不是"某次构建顺手带进去了"）。判定逻辑在 `companion-kit` 的 `judgeLicense()`。
```

汇总字段 `assetFilesInPayload` 的扩展名集合（`:238-240`）与上面的禁用清单**必须一致**，
注释（`:235-237`）写明理由：两处各写一份就会漂移（"扫描拦了但汇总没算"或反过来）。

## 4. 工具执行器的固定顺序

### 4.1 顺序与理由（`tool-registry.ts:95-101`，逐字）

```
/**
 * 统一执行。
 *
 * 顺序**不能变**：先判定权限 → 再校验参数 → 再（必要时）确认 → 才执行。
 * 反过来（先校验参数）会把"这个工具你根本没权限用"变成"你的参数写错了"，
 * 既误导模型也误导用户。
 */
```

五个阶段在 `invoke()`（`tool-registry.ts:102-176`）里的落点：

| 序 | 阶段 | 代码位置 | 失败时的 `decision` | `ok` |
|---|---|---|---|---|
| 0 | 未知工具 | `:107-111` | `unknown-tool` | `null` |
| ① | **权限判定**（`o.decide(spec.permissionKind)`，唯一真源是 `permission-store`） | `:113-118` | `denied` | `null` |
| ② | **参数校验**（`spec.params.safeParse(params)`，zod） | `:120-126` | `error` | `null` |
| ③ | **用户确认**（仅 `needs-confirm` 档） | `:128-144` | `needs-confirm` | `null` |
| ④ | **执行（带超时）**（`Promise.race` + `AbortController`） | `:146-165` | `allow` / `timeout` / `error` | `true`/`false` |
| ⑤ | **审计**（每个分支都写，无遗漏） | `:109,116,124,132,141,160,171` | — | — |

**"权限先于参数"为什么重要**：如果把参数校验提到前面，一个 `payment.pay`（永久禁止）的调用
拿到的回复会变成"你的参数写错了"——用户和模型都会去**修参数**，
而正确答案是"这个能力**永远不会**被执行"。顺序反了，错误信息就会**主动误导修复方向**。

**超时必须真的生效**：`setTimeout(() => ctl.abort(), spec.timeoutMs)`（`:149`）+
`Promise.race` 里挂 `abort` 监听（`:152-157`）；超时走 `catch` 分支并记 `decision: 'timeout'`。
`register()` 还会**在注册期**就拒绝没有超时的工具（`:81`：`必须声明正数 timeoutMs（没有超时的执行会拖住整个应用）`），
同理拒绝没有 `permissionKind` 的工具（`:82`）。`kit.test.mjs` 有两个用例分别钉住这两条与超时行为
（`★ 超时必须真的生效，并记成 timeout（而不是挂住）`）。

### 4.2 审计 `ok` 是**三态**：`null` = 从未执行，`false` = 执行了但失败

`AuditSink` 的形状（`types.ts:316-327`）里 `ok: boolean | null`；
`tool-audit.ts:10-13` 把这条纪律写成文件头第 ② 条，逐字：

```
*   ② **`ok` 只由执行器写**：审计层不猜、不推断。未执行时恒为 `null`
*      （`null` ≠ `false`：前者是"没执行"，后者是"执行了但失败"）；
```

`toolAuditDigest()`（`tool-audit.ts:110-127`）把它变成三个**能看见的数**：

```ts
neverExecuted:  records.filter(r => r.ok === null).length,   // 被拒 / 未确认
executedOk:     records.filter(r => r.ok === true).length,
executedFailed: records.filter(r => r.ok === false).length,
```

**为什么必须区分**：把"被权限挡住"和"跑了但失败"混成一个数，
会让"我到底有没有执行过危险操作"变成一个**答不上来**的问题。
实测读数（引用 `kit.json`，非本会话重跑）：`total: 6`、`byDecision: {denied: 6}`、
`neverExecuted: 6`、`executedOk: 0`、`executedFailed: 0` —— 6 个工具**一个都没执行过**。

### 4.3 摘要只记"哈希 + 原长"，格式**只有一种**

`digestOf()`（`tool-audit.ts:34-43`）与 `defaultDigest()`（`tool-registry.ts:46-55`）是**同一种格式**：

```
sha256:<12 位十六进制>:len=<原文长度>
```

校验正则在 `tool-audit.ts:46`：`export const DIGEST_PATTERN = /^sha256:[0-9a-f]{12}:len=\d+$/`。
`capabilities/index.ts:111-112` 把审计层与执行器**绑到同一个函数**，注释写明理由：
"与审计层共用**同一个**摘要函数（格式只有一种，'格式正确'才可机械校验）"。

`recordToolCall()`（`tool-audit.ts:69-102`）再做一次长度截断（`tool` 64 / `paramsDigest` 80 /
`reason` 300 / `resultDigest` 80），内存环保持最近 `MAX_RECORDS = 200` 条。
**它没有正文入参** —— 不是"过滤掉正文"，而是**结构上就没有地方放正文**（`:85` 的注释原话）。

### 4.4 给模型看的清单：`denied` 的不进（`tool-registry.ts:187-201`，逐字）

```
 * ⚠ `denied` 的工具**不进清单**：把模型根本不能用的工具告诉它，
 *   只会让它反复尝试并给用户"我做不到"的假象 —— 那正是"模型伪造成功"的温床。
```

`createForbiddenTools()`（`future-adapters.ts:123-139`）注册了**四个永久禁止**的工具：
`payment.pay`（支付/下单）、`credential.read`（读凭据文件）、`system.settings`（改系统设置）、
`input.simulate`（模拟键鼠）。它们 `run()` 一律抛
`` `${name} 永久禁止执行（权限硬下限）` ``（`:131`）。
注释（`:119-122`）说明了"注册进去但永远不可用"的意义：
"让'本应用存在哪些被永久禁止的能力'成为**可枚举的事实**，而不是散落在文档里的一句承诺"。

## 5. 存储迁移

### 5.1 迁移链：三种情况 + 7 个原因码

`migrateStore(raw, desc)`（`store-migrator.ts:74-138`）的文件头注释（`:65-73`）把语义归纳为三种情况：

```
 *   ① 数据版本 === 目标版本 ⇒ 原样返回（`steps` 空）；
 *   ② 数据版本 < 目标版本 ⇒ 逐级迁移；
 *   ③ 数据版本 > 目标版本 ⇒ **拒绝**（`future-version`），调用方必须**保留原文件**
 *      并如实提示用户"数据来自更新版本"，**不得清空**。
```

`MigrationOutcome.reason` 的实际取值集合是 **7 个**（`store-migrator.ts:35`，逐字）：

```ts
reason: 'ok' | 'no-version-field' | 'invalid-version' | 'future-version' | 'missing-migration' | 'migrate-threw' | 'cycle'
```

（`no-version-field` 有**两个**返回点 —— 目标版本为 1 时接受、更高版本时拒绝，
所以函数里一共 9 个 `return`，但原因码只有 7 个。若别处把它概括成"五种结果"，以这 7 个为准。）

链条自洽性由 `validateMigrations()`（`:40-56`）校验：`to` 必须等于 `from + 1`（逐级才可重放）、
`from` 不得重复、链必须连续。**迁移函数必须是纯函数**（`types.ts:331-337` 与文件头 `:18`）。

### 5.2 `future-version` 规则：数据比程序新 ⇒ 拒绝读，**保留原文件**

代码（`store-migrator.ts:101-107`，逐字）：

```ts
  if (from > desc.version) {
    return {
      ok: false, data: raw, fromVersion: from, toVersion: desc.version, steps: [],
      reason: 'future-version',
      detail: `数据版本 ${from} 比本程序支持的 ${desc.version} 新（可能装过更新版）—— 已保留原文件，不做任何修改`,
    }
  }
```

注意 `data: raw` —— 失败时**带回的是原始数据**，不是半迁移的中间态
（`migrate-threw` 分支同样 `data: raw`，`:125`）。
`kit.test.mjs` 有 ★★ 用例：`★★ 数据版本比程序新 ⇒ 拒绝读且**保留原数据**（降级安装不该丢数据）`。

### 5.3 它防止的具体后果：12 个存储全是 `version: z.literal(1)`

`store-migrator.ts:5-8` 把这个问题写成了"为什么必须有它"，逐字：


## 6. 投影边界（主进程 → renderer）

### 6.1 renderer 拿不到路径，是设计；但有一处被"说明性字段"绕过了

`ResolvedAsset.path` 是**绝对路径**，`types.ts:232` 明确写着它的边界：
"绝对路径（**只在主进程内部流转**；renderer 只能拿到 app:// 相对形式或 id）"。

`kit:assets` 的出参因此**不返回 `path`**（`ipc.ts:657-667`），只投影 `id` / `license` / `verdict`。

### 6.2 真实泄漏（探针抓到的）

泄漏链完整复现如下：

1. `assets/models/catalog.json:13` 的 `source` 字段写着
   `Mate Engine DLC（<盘符>:\…\repos\Mate-Engine），目录内无独立许可文件；仅本机私有使用，不得分发`
   —— 一个**纯说明性**字段，里面带绝对路径；
2. `inferLicense()`（`asset-resolver.ts:92-104`）在判为 `private-only` 时把
   `note: str(raw.source) ?? '清单标注为不可再分发'` —— **原样**搬进 `license.note`；
3. `kit:assets` 的出参把 license **原样**投影给 renderer —— 这是**修复前**的行为，
   由 `asset-adapter.ts:134-144` 的注释证实（"而 `inferLicense()` 会把它带进 `license.note`
   ⇒ **随 `kit:assets` 出参回到 renderer**"）。本会话看到的是**已修**版本：
   `ipc.ts:665` 现在调的是 `projectLicenseForRenderer(a.license)`；
4. ⇒ 绝对路径**随 `kit:assets` 出参回到了 renderer**。

也就是说：**"renderer 拿不到文件路径"这条设计被一个说明性字段整条绕过**。
抓到它的是探针的两条断言（`bootstrap.ts:3499` 与 `:3520`）：

```ts
mark('kit.no-abs-path-in-output', !new RegExp(String.raw`[A-Za-z]:[\\/]`, 'i').test(capJson))
mark('kit.assets.no-abs-path',   !new RegExp(String.raw`[A-Za-z]:[\\/]`).test(JSON.stringify({ u: a.usable, r: a.rejected })))
```

### 6.3 `redactPaths()`（`asset-adapter.ts:145-161`）

四道替换 + 一道**最后兜底**。文件头注释（`:134-144`）逐字记录了这次泄漏：

```
 * ★ 脱敏：把任意文本里的**绝对路径**替换成占位符。
 *
 * 为什么必须有它（实测抓到的泄漏）：`catalog.json` 的 `source` 字段写着
 * "Mate Engine DLC（<盘符>:\…\repos\Mate-Engine）…"，
 * 而 `inferLicense()` 会把它带进 `license.note` ⇒ **随 `kit:assets` 出参回到 renderer**。
 * 结果就是"renderer 拿不到文件路径"这条设计被一个**说明性字段**绕过了 ——
 * 探针正是靠"投影里不得出现盘符"这条断言抓到它的。
 *
 * 投影边界（主进程 → renderer）必须做这件事，而不是指望每个来源字段都干净。
```

> **引用说明**：上面这段是**逐字引用**，只把原文里的那一段**本机绝对路径**换成了
> `<盘符>:\…\repos\Mate-Engine`（本文全篇不打印本机路径，与 §6 的处置口径一致）。
> 原文的完整串可以在 `apps/desktop/src/main/capabilities/asset-adapter.ts:137-139` 读到。

实现（`:148-160`）：① Windows 驱动器路径（字符类里**显式允许分隔符**，否则只吃掉盘符那一小段）；
② UNC；③ 兜底 —— 中文/空格把路径切碎后残留的"两段以上分隔符"片段；④ 类 Unix 多级路径（至少三级，避免误伤普通斜杠文本）。
**最后一道兜底**（`:156-160`）是这次修复最关键的一行：

```ts
  /**
   * 自查：万一还有残留盘符（正则被改坏时最容易发生），
   * 就把整段换成占位符 —— **宁可少给信息，也不漏路径**。
   */
  return /[A-Za-z]:[\\/]/.test(out) ? '<redacted: contains absolute path>' : out
```

即：**即使 ①②③④ 全部被改坏，输出里也不可能残留盘符**。
`kit-redact.test.cjs` 有一条专门用例构造畸形串来钉住它
（`★ 兜底：无论正则怎么改，输出里都不允许残留盘符`，输入 `'X:\\'` 与 `'a D:\\ b'`）。

### 6.4 `projectLicenseForRenderer()`（`asset-adapter.ts:167-176`）

只把**自由文本**过关：`licenseSource` 与 `note` 过 `redactPaths()`；
结构字段（`provenance` / `redistributable` / `commercialUse` / `license` / `attributionRequired`）**不动**。
并且**返回新对象**，不改入参 —— `kit-redact.test.cjs` 用 `assert.equal(lic.note.includes('F:\\'), true)`
钉住了"主进程内的审计仍然看得到完整信息"这一条。
`licenseSource === null` 时保持 `null`（不能变成字符串 `"null"`，也有用例）。

## 8. 本阶段修复的真实缺陷

> 以下四条是**题面点名的必需项**，我把每条写成"症状 → 根因 → 修法"。
> 每条都给出**落在源码里的证据串**（原始注释），因为这些缺陷的描述本身就被作者写进了注释里。
> §8.5 之后是本会话**新发现、尚未修**的缺口，单独成段以免混淆。

### 8.1 `callJson` 把 Promise 序列化成了 `{}`，表现为"所有通道都坏了"

- **症状**：探针读 `kit:capabilities` / `kit:assets` / `kit:tool-audit` / `kit:stores`
  全部拿回**空对象** `{}`，读起来像"四个新通道一个都没注册"。
- **根因**：探针里的取值封装早期写成 `` `JSON.parse(JSON.stringify(${expr}))` ``，
  而 `expr` 是 `window.airimate.kitCapabilities()` 这类**返回 Promise 的表达式** ——
  `JSON.stringify(Promise)` 得到 `"{}"`，**await 发生在 stringify 之后**。
- **修法**：改成"**先 await 表达式再 stringify**"。原文（`bootstrap.ts:3443-3455`，逐字）：

  ```
   * ⚠ 必须**先 await 表达式再 stringify**。
   *
   * 踩过的坑（这一轮就是靠它定位的）：早期写的是
   * `JSON.parse(JSON.stringify(${expr}))`，看起来没问题，但 `expr` 若是
   * **返回 Promise 的表达式**（`window.airimate.xxx()` 全是），
   * `JSON.stringify(Promise)` 得到 `"{}"` ⇒ 探针拿到一个**空对象**，
   * 表现为"所有通道都失效"（而其实一切正常）。
   * 这是**测量工具自伤**，比真缺陷更难查：所有读数一致地"空"，
   * 看不出是工具的问题而不是产品的问题。
  ```
  ```ts
  const callJson = async (expr: string): Promise<Record<string, unknown>> =>
    await call(`(async () => { try { return JSON.parse(JSON.stringify(await (${expr}))) } catch (e) { return { error: String(e) } } })()`) as Record<string, unknown>
  ```
- **顺带留下的诊断**：`bootstrap.ts:3461-3479` 保留了 `kitRaw` / `apiMethods` / `control` / `stepByStep`
  四组**对照读数**，用于区分"方法不存在 / 返回值 undefined / 序列化丢键 / 抛错"四种情况。
  `kit.json` 里能看到它们：`kitRaw.ok: true`、`apiMethods` **88** 个方法（含 4 个 `kit*`：
  `kitAssets` / `kitCapabilities` / `kitStores` / `kitToolAudit`）、
  `stepByStep: { hasMethod: "function", awaited: "object", valueOk: true, jsonLen: 5086 }`。

### 8.2 审计占位摘要 `sha256:startup:len=0` 破坏了"摘要格式只有一种"

- **症状**：探针的"每条审计的摘要都是合法格式"断言**失败**。
- **根因**：启动期记账（"哪些工具被权限挡住了"）没有真正的参数，早期随手写了一个
  占位摘要 `sha256:startup:len=0` —— 它不是 `sha256:<12 位十六进制>:len=<数字>`，
  于是 `DIGEST_PATTERN` 校验不过。原文（`tool-audit.ts:29-32`，逐字）：

  ```
   * 为什么不写"用 `companion-kit` 的 defaultDigest 就行"：启动期记账（"哪些工具被
   * 权限挡住了"）没有真正的参数，需要一个**占位摘要**。早期我随手写成
   * `sha256:startup:len=0` —— 于是"每条审计的摘要都是合法格式"这条判据被
   * 探针抓成失败。格式必须**只有一种**，否则"格式正确"就没法机械校验。
  ```
- **修法**：启动期记账也调**同一个** `digestOf()`（`bootstrap.ts:632-641`）：

  ```ts
  for (const t of b.tools.list()) {
    if (t.decision === 'denied') {
      recordToolCall({
        callId: `startup-${t.name}`, tool: t.name, decision: 'denied',
        reason: `权限硬下限/未启用：${t.permissionKind}`, ok: null, durationMs: null,
        // ★ 用**同一个**摘要函数（占位也要合法格式，"格式正确"才能机械校验）
        paramsDigest: digestOf(`${t.name}:startup-denied`), resultDigest: null,
      })
    }
  }
  ```
  摘要在 `capabilities/index.ts:111-112` 被绑定为 `digest: (v) => digestOf(v)`，
  单测 `defaultDigest 稳定且不泄漏原文` 与 `★★ 审计里没有参数原文（只有 sha256 前 12 位 + 原长）` 覆盖。

### 8.3 `catalog.json` 的 `source` 说明文字把本机绝对路径带回了 renderer

- **症状**：探针断言"投影里不得出现盘符"失败；`kit:assets` 的 `license.note` 里带着
  `<盘符>:\…\repos\Mate-Engine`。
- **根因 / 修法**：全文见 **§6.2 / §6.3**。一句话：**说明性字段绕过了整条路径边界设计**，
  修法是 `redactPaths()` 的四道替换 **+ 最后兜底**（"宁可少给信息，也不漏路径"），
  并在 `ipc.ts:665` 的投影里对 `licenseSource` / `note` 逐条过关。
- **本次实测的两条读数**（引用 `kit.json`）：`kit.no-abs-path-in-output: true`、
  `kit.assets.no-abs-path: true`；
  并且 `assetsCheckedSample` 里 `lazuli` 的 `note` 已经被写成
  `"Mate Engine DLC（<path>），目录内无独立许可文件；仅本机私有使用，不得分发"` —— **占位符生效**。

### 8.4 不为新通道重建 preload / main，通道双向一一对应会失败

- **症状**：`m1-contract.test.cjs` 的 ★ 用例失败 ——
  "preload 内联通道与 shared.IPC 双向一一对应"：`missing` 或 `extra` 不是空数组。
- **根因**：那条用例**不是**读源码，而是 `require` **编译产物**
  （`m1-contract.test.cjs:33-34`）：

  ```js
  const SHARED = require(path.resolve(__dirname, '..', '..', '..', 'packages', 'shared', 'dist', 'index.js'))
  const PRELOAD = require(path.resolve(__dirname, '..', 'dist', 'preload', 'index.js'))
  ```

  断言（`:61-64`）：`missing === []`、`extra === []`，并逐个键比**值**也相等（`:67`）。
  所以改了 `packages/shared/src/ipc.ts` / `apps/desktop/src/preload/index.ts` 却**不重建**，
  测试读到的仍是旧产物 ⇒ 新通道"少在 preload 里"⇒ 失败。
- **修法**：重建 `@airimate/shared` 与 desktop 的 preload / main。
- **诚实划界**：这条我**只验证了机制与当前状态**，**没有**复现失败本身
  （没有回滚产物再跑一次）。我能给出的实测事实是：
  ① `apps/desktop/dist/preload/index.js` 里四个通道字符串命中数 = **4**（§7.10）；
  ② `apps/desktop/dist/main/capabilities/*.js` 存在（写入 `2026/10/2 0:05:31`）；
  ③ 含该用例的 `m1-contract.test.cjs` 在 `run-all` 的 234/234 里**通过**。

### ④ 修复过程中抓到的**第二层缺陷**（这是最值得记的一条）

做真实的 v1→v2 演练时发现：**迁移器修好了"能迁"，却卡在"迁完不符合形状"**。

- 现象：迁移日志显示成功（`from=1 to=2 steps=1`），但紧接着
  `文件校验失败 → 使用默认值`，`issues: version:Invalid literal value, expected 1` ⇒ **数据照样丢**。
- 根因：各 store 的 schema 写的是 `version: z.literal(1)`（必需字段），
  而迁移把 `version` 变成了 2 ⇒ 校验必然失败。
- 修法：`json-store.ts` 在 **校验前** 把 `version` **归一化成当前版本**
  （`normalizeVersion()`）。试过"直接删掉 version"，那样 schema 会报"必须提供 version"，
  **两条路都通向回退默认值** —— 归一化是唯一让两种输入都通过的写法。
- 复现（真实数据、真实迁移、断言字段存活）：

```powershell
# 用一条自建 v2 描述子把整条链路跑穿：读盘 → 迁移 → schema 校验 → 缓存
node --test apps/desktop/test/store-migration.test.cjs
# 其中 "★★ 真实 v1→v2 迁移：用户数据必须活下来（迁完还要过 schema 校验）"
```

这条用例的价值在于：**它抓到的缺陷，"迁移器单测通过"完全掩盖不了** ——
只有把 store 层一起跑才看得见。光测库、不测接线，等于没测。

### ⑤ 运行形态判定又错了一次（已修，且加了单测）

组装载荷里跑 `--probe kit` 时发现 `profile=packaged`、`kit.active-avatar=false`
（⇒ **装完没有角色**）。两次都错在同一个判断上：

- 坑 A：把"存在 `AIRIMATE_WORKSPACE`"当成 packaged。
- 坑 B（修 A 之后又踩）：只看 `app.isPackaged`。本项目把 `electron.exe` **改名**成
  `AiriMateOne.exe`，而 Electron 判定"打包"的依据正是可执行文件名 ⇒

### 11.2 ★★ 私有许可资产在打包载荷里**被机械拒绝**（② 的运行期证据）

同时做了一个**对照实验**：**同一个文件路径**换成 `redistributable: true` 的许可，
必须**能用** —— 只证明"私有被拒"是不够的，一个永远拒绝一切的实现也能通过那条断言。

⇒ 载荷未被改动。新增判据四条：`kit.assets.private-rejected-when-packaged` /
`private-not-usable` / `private-not-selected` / `control-usable-when-licensed`。

**这一版注入改掉了第一版的两个毛病**（都是"写下了才发现"的）：

1. **断言用前缀匹配是假通过**。第一版写的是 `String(hit.reason).startsWith('denied')`。

   现在占位文件由探针自己造，与机器无关。

> 这两条是**代码审计**发现的，不是测试发现的 —— 说明"探针自己也是代码，也要按同样的标准审"。

### 11.3 ★ 抓到缺陷一：绝对路径从**另外两个字段**漏回 renderer

打包形态一跑，`kit.no-abs-path-in-output` 立刻红，实测漏出：

```
"清单不存在：F:\\deepseek harness\\AI女友\\新工程\\dist-package\\resources\\workspace\\assets\\models\\catalog.json"
```

来源有两处，都在 `asset-resolver.ts`：`readCatalog()` 的 `清单不存在：${file}`，
以及 `rejected[].detail` 的 `文件不存在：${src.path}`。它们经由
`kit:assets`（`assets.detail` / `assets.rejected[].detail`）与 `kit:capabilities`
（`adapters[].unavailableReason`）回到 renderer。

**这是同一个洞的第二次发作**：第一次修的正是路径泄漏，但修法是**逐字段点名**
（只投影 `license.note` / `licenseSource`）。逐字段修补的病根是
"依赖每次加字段都记得再点一次名"，而漏的永远是忘了的那次。
更糟的是探针里那句为自己的偷懒辩护的注释 ——
"检查整个响应体是**过严**的断言" —— 等于给泄漏留了一块**自留地**。

修法：在**唯一出口**做一次递归清洗。

```ts
// asset-adapter.ts
export function redactDeep<T>(value: T, depth = 0): T   // 每个字符串都过 redactPaths
// ipc.ts：四个 KIT 只读通道的返回值**全部**包在 redactDeep 里
```

配套：

- `ipc.ts` 里那句"出参里**没有密钥、没有绝对路径**"的注释是**假的**，已改成
  如实说明 + 记下"同一个错误犯了第二次"；
- 探针新增 `kit.boundary-no-abs-path` / `kit.boundary-no-secret`：
  对**四个通道的合并载荷**做断言（新增字段自动被覆盖）；
- 单测 `★★ 四个 KIT 通道的出参都走深度清洗` 做**源码级断言**：
  任一通道的 return 里丢了 `redactDeep` 就会红。

**刻意不过度脱敏的一处**：`privacy:summary.userDataDir` 会返回
`C:\Users\<用户>\AppData\Roaming\AiriMateOne`，它**不在**上述断言集合里 ——
把"你的数据在哪"告诉用户本人是本应用的功能（那是它自己的数据目录，
不含仓库来源信息），不是泄漏。这个边界写进了 `ipc.ts` 与探针的注释，
免得后来的人"顺手"把它也 redact 掉、让隐私页失去意义。

### 11.4 ★ 抓到缺陷二：打包形态下判据把"许可生效"误报成失败

`kit.active-avatar` 原来无条件要求"必须有 active avatar"。而打包载荷里
**没有**可再分发的角色资产（M5 的资产替换还没做），私有资产又被**正确地拒绝** ⇒
`activeId` 就是 `null`。于是这条判据把 **② 想要的行为**判成了失败。

危险之处不是这条红了，而是**它会把人往反方向推**：为了让判据变绿，
后来的人会去放宽许可闸门 —— 正好把 ② 拆掉。

修法：按形态分别断言，两边都要**可解释**：

- `development` ⇒ 必须有选中项（回归守卫）；
- `packaged` ⇒ 允许没有，但 `unavailableReason` **必须非空**给出原因。
  "不可用且说不清为什么"才算失败。

`kit.assets.selected-in-development` 原来写的是
`kit.profile !== 'development' || typeof a.selectedId === 'string'`
—— 意思是"非开发形态就不要求"。它的问题不是松，而是**它从来不问"那为什么没有"**。

### 11.6 ★★ 补上 ① 里**唯一没有适配器**的一类：动作（motion）

这是本轮的第三个发现，也是最实质的一个。

`CapabilityKind` 从第一天起就声明了 `'motion'`（"动作：clip 来源与解析"），
但**从来没有注册过任何 motion 适配器**。实测：`byKind.motion.registered = 0`。

为什么这不是"少写一个类"这么轻：动作资产的来源与角色**完全一样**是私有的 ——
`assets/models/catalog.json` 的 `motions` 块写着
"由 Mate Engine 的 `.anim` 动捕剪辑本地转换为 VRMA；**转换产物同样不得分发**"。
而业务代码（`motion-state.ts`）直接 `readdirSync(appPaths().motionDir)`：
**没有适配层，也没有任何许可判定**。
换句话说：**动作是本项目唯一一类能绕过许可闸门进入分发载荷的资产。**

补法（三层）：

| 层 | 文件 | 作用 |
| --- | --- | --- |
| 纯逻辑 | `packages/companion-kit/src/motion-resolver.ts` | `resolveMotions()` / `inferMotionLicense()`：**不读盘**，吃"目录里有哪些文件 + 清单写了什么"，吐出可用 clip 与被拒原因 |
| 适配器 | `apps/desktop/src/main/capabilities/motion-adapter.ts` | 读盘、缓存、注册为 `motion.vrma-catalog`；`available` 由**实测**决定 |
| 接线 | `motion-state.ts` 的 `setMotionSource()` | 业务模块改为消费**注入**的来源，不再自己读盘 |

**用注入而不是 import** 的原因：`motion-state → capabilities → motion-state` 会成环，
本工程已经因为 ESM 环踩过一次 TDZ 崩溃（`event-sink.ts` 就是为拆环抽出来的）。
注入还有一个好处：没接线时 **不假装有动作**（`failed` 里如实写"动作来源未接入"），
而不是回退到自己读盘 —— 回退会让适配层形同虚设，也会让许可闸门被绕过。

#### 11.6.1 ★ 「少列一项」这个错误在同一轮里犯了**三次**

#### 11.6.2 ★ 许可文本已经写了结论，就不该判成"来源不明"

第一版 `inferMotionLicense()` 只看 `redistributable` 字段，没写就归 `unknown`。

而不是 `denied-packaged-unknown-license`（"我们什么都不知道"）——

> 修法分两步：① 源头就不生成路径（`motion-state.ts` + resolver）；② 判据覆盖 `app:diagnostics`。

#### 11.6.5 ★ 第五处不一致：适配器说"拒了"，协议层却还愿意把文件喂出去

补完适配器之后顺着看了一层，发现一个**自相矛盾**的状态：

- `capabilities/motion-adapter.ts` 在打包形态下判定"这些动作不可再分发 ⇒ 不可用"（`clips: []`）；
- 而 `asset-protocol.ts` 的 `grants()` **无条件**把 `p.motionDir` 注册成
  `app://asset/` 的授权根。

两条结论同时成立就是矛盾：**适配器说不能用，协议层照样愿意把那个目录里的文件交出去。**
正常路径下 renderer 拿不到 clip id、也就不会去请求 ——
但"授权根"是一条**独立的防线**，它不该依赖"调用方不知道 id"这种默契。

修法：授权根跟着判定走。

```ts
// motion-state.ts
export function motionAssetRoot(): string | null {
  if (!source) return null
  if (motionStatus().clipCount <= 0) return null   // 判定无可用动作 ⇒ 不放开目录
  return source.assetRoot()
}
// asset-protocol.ts：没有授权根就**不注册** asset 主机名 ⇒ app://asset/... 一律 404
```

缺失时**不注册**而不是"注册一个空目录"：前者的语义是"这个能力不存在"，
后者在排障时会看起来像"目录配错了"。

三条新用例：授权根未接线为 null / 判定无可用动作 ⇒ 授权根 null（含"有可用动作时才给出"的对照）/
源码级禁止再把 `motionDir` 写死成授权根。

## 12. 形态裁定（2026-10-03，用户决定）—— M5 的资产替换**不做**

**裁定**：本产物**永久保持"私有自用"形态**，**不替换**为可再分发/可商用角色资产。

**这条裁定关掉了本文 §9 与 §11.8 里两条"不可能验证"的空白**，措辞必须跟着改，别留着当待办：
