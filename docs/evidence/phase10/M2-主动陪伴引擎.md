## 3. 开机问候 / 日程播报 / 早安电台

### 3.1 问候与日程播报

- **先采样再判阻断**，顺序不能反（`proactive-engine.ts:564-575`）。踩过的坑写在注释里：
  早期版本先判阻断（用上一次的采样）再采样，于是"会议刚结束"这一 tick 仍按 `meeting` 判 ⇒
  队列要等下一个 tick 才补发；单测里 tick 是瞬间连续的，表现为"补发永远不发生"。
- **补发优先**：`runTick()` 里 `flushReminderQueue()` 与 `flushOutbox()` 排在最前面
  （"阻断刚结束的那一刻最该做的事"）。
- **问候文案**：`hhmm(now) < '12:00' ? '早上好' : '你回来啦'`；未配置可用供应商时追加
  `（提醒：还没配置可用的模型供应商，我现在只能陪你说话）`。
- **问候被阻断时 `speak` 被强制降级**：`enqueue({ ...e, speak: false }, ...)` —— 队列里的东西一律不发声。

### 3.2 早安电台六节与"没有数据就不说"

结构（`morning-radio.ts:152-157`）：

```

最长连续段 ≥90 分钟、昨天最长连续 ≥120 分钟、被阻断采样占比 >50% —— 四条触发条件，
最多给 3 条；**没有数据就返回空数组**（单测：`adviceFromStats()` 在无数据时 `deepEqual([], …)`）。

`disclosures` 的取值来源（`morning-radio.ts:125-136`）：

```
天气不可用         → `天气：${unavailableReason ?? '不可用'}`
天气可用           → `天气来源：${source ?? '未知'}`

### 3.3 30–60 秒是怎么被"钉死"的（含一次真实失败与修复）

**算法（原文）**：

```ts
// apps/desktop/src/main/morning-radio.ts:22-27
export const CHARS_PER_SECOND = 4.2
export const TARGET_MIN_SECONDS = 30
export const TARGET_MAX_SECONDS = 60
const MIN_CHARS = Math.floor(TARGET_MIN_SECONDS * CHARS_PER_SECOND)   // 126
const MAX_CHARS = Math.floor(TARGET_MAX_SECONDS * CHARS_PER_SECOND)   // 252

// :41-44
export function estimateSeconds(text: string): number {
  const chars = [...text.replace(/\s+/g, '')].length
  return Math.round((chars / CHARS_PER_SECOND) * 10) / 10
}
```

**裁与补的策略**：超长时按优先级裁 `资讯 → 建议`（**不裁日期与天气** —— 那两节是用户最先要听的），
最后再兜一次硬裁并如实标注；偏短时按句子长度**递减**顺序循环追加 `fillers`，**补到够为止**。

**代码注释记录的那次真实失败（逐字引用，`morning-radio.ts:167-175`）**：

```
⚠ 这里踩过一次：原来的实现只补**一句**，而"离线 + 无日程 + 无资讯"时
  基础稿只有 ~26 字（`16.2s`），补一句仍不到 126 字 ⇒ "30–60 秒"这条
  用户要求实际上**没有达标**（单测抓出来，第二版补到 123 字仍然差 3 字）。
  现在：句子按长度递减（保证"最少几轮"就能补够），且**循环到够为止**，
  最后再兜一次"很短但真实"的句子 —— 不允许出现"差一点点就达标"的状态。
```

> **说明**：`16.2s` 与 `123 字` 这两个数字来自**源码注释**（作者记录的当时实测），
> **不是本会话重跑复现的**。本会话能验证的是**当前实现确实补到了下限** —— 见下面这条单测。

**当前状态（本会话实测的单测断言）**：

```
test('早安电台：30–60 秒是**硬要求**（口播稿字数在 126–252 之间 + 边界兜底）', ...)
  const chars = [...r.content.script.replace(/\s+/g, '')].length
  assert.ok(chars >= 126 && chars <= 252, `口播稿字数 ${chars} 不在 126–252 之间`)
```
该用例在默认（离线、无城市、无资讯）配置下**通过**。

**另一个诚实点**：补足用的是"**很短但真实**"的固定句子（filler），
即"时长达标"部分靠的是**真实但通用**的话术而不是编造内容 —— 如果连 filler 都补不满，
代码会选择**如实标注**（`disclosures` 加"口播稿短于 30 秒的常规时长"）而不是继续灌水。

### 5.2 为什么"采样不可用"要当作**被阻断**

`blocker.ts:11-13` 的原文理由：

```
· **采样不可用时保守处理**：`available:false` 时返回 `focus`（视为不可打扰），
  而不是 `none` —— 读不到阻断状态时弹窗打断用户，代价比晚一点提醒大得多。

```

单测把这条钉住了：`act({ available:false, unavailableReason:'探针脚本不存在' })` ⇒
`r.blockReason === 'focus'` 且 `h.emitted.length === 0`。
换句话说：**探针挂掉 ⇒ 引擎变安静，而不是变吵**。

## 6. 冷却 / 开关 / 优先级

```ts
// apps/desktop/src/main/blocker.ts:98-109
export function inCooldown(kind, lastFiredAt, now = Date.now(), policy = loadReminderPolicy()) {
  if (lastFiredAt === null) return { cooling: false, untilMs: null, remainingMinutes: 0 }
  const windowMs = policy.cooldownMinutes[kind] * 60_000
  const until = lastFiredAt + windowMs
  if (now >= until) return { cooling: false, untilMs: until, remainingMinutes: 0 }
  return { cooling: true, untilMs: until, remainingMinutes: Math.ceil((until - now) / 60_000) }
}
```

- **默认冷却**：`continuous 60 / sedentary 60 / night 720 / greeting 480 / radio 60`（分钟）。
- **冷却只由"真的送达过"驱动**：`lastFiredAtOf(kind)` 只看 `firedAt`；排队中的提醒不消耗冷却
  （单测：`markQueued` 后 `lastFiredAtOf('continuous') === null`，`markFired` 后才变成数字）。
- **三层防重复**（`reminder-store.ts:13-17`）：① 同类冷却窗口；② 同一天 `dedupeKey`
  （`continuous:<day>` / `sedentary:<day>` / `night:<day>` / `sched:<id>:<day>`）；
  ③ 状态机只有 `pending` 能被触发。
- **可关闭开关**：`proactiveEnabled`（总开关）+ 六个能力开关，全部在
  `SettingsPatchSchema` 里（renderer 可写），关掉后**连队列都不进**。
- **三级优先级 → 呈现方式**：`important → popup`、`normal → popup`、`silent → inbox-only`；
  `ProactiveToast.vue` 里 `important` 用 `role="alert"`，其余用 `role="status"`（礼貌级）。
- **`silent` 永不弹窗、永不发声**；**`important` 也不突破"静音时段不发声"**（刻意决定，
  见 §1.26/§1.27）。`QuietHours.allowImportant` 只放宽到"进队列 + 角标"。

## 7. 队列上限与重试上限

```ts
// apps/desktop/src/main/reminder-store.ts:290-305
export function enforceQueueLimit(): string[] {
  const max = loadReminderPolicy().maxQueue
  const queued = queuedReminders()
  if (queued.length <= max) return []
  const droppable = queued.filter(r => r.priority === 'silent').slice(0, queued.length - max)
  if (droppable.length === 0) {
    // 全是重要/普通级：只记警告，**不丢**（宁可队列长一点也不丢用户的要紧事）
    log().warn('提醒队列超限但无可丢弃项（重要/普通级全部保留）', { queued: queued.length, max }, 'reminder.queue.overflow')
    return []
  }
  // …把被丢的标记为 cancelled 并写 lastError='队列超限被丢弃'
}
```

- **只丢最旧的 `silent` 级**；被丢的条目**不是静默消失**：状态转 `cancelled`、
  `lastError = '队列超限被丢弃'`，并打日志 `reminder.queue.drop-silent`。
- **全是重要/普通级 ⇒ 不丢**（`dropped` 返回 `[]`，并有 `reminder.queue.overflow` 警告）。
- **重试上限**：`markAttemptFailed()` 在 `attempts > maxRetries`（默认 3）时把状态转 `failed`
  并写 `lastError`，同时 `log().warn(..., 'reminder.failed')` —— 不做无限重试。
- 内存侧的事件缓冲 `outbox` 也有上限（`maxQueue ?? 50`）：超限先丢最旧的 `silent`，
  没有 `silent` 才丢最旧一条，两种都打日志（`proactive.queue.drop` / `proactive.queue.drop-oldest`）。
