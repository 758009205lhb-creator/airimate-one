## 2. 两条"默认不执行"的语义

这两条是本阶段安全设计的核心，也都是**可机械复核**的，不是注释里的承诺。

### 2.1 `needs-confirm` 有三条拒绝路径，只有**显式同意**才得到 `true`

`tool-confirm.ts:5-11` 把这条纪律写成了文件头，逐字：

```
 * 用户要求："普通操作需确认"。这条要求的实现有一个**最容易做错的点**：
 *   没有确认入口时该怎么办？
 *   如果答案是"那就直接执行"，那 confirm 档就被悄悄降级成了 allow ——
 *   整条三档设计当场失效。所以这里的缺省方向是 **拒绝**：
 *   · 没有确认通道 ⇒ `false`（不执行）；
 *   · 用户没回应（超时）⇒ `false`（不执行）；
 *   · 用户点拒绝 ⇒ `false`（不执行）。
 *   只有**显式点了同意**才是 `true`。三种默认都是"不执行"，这是刻意的。
```

| 拒绝路径 | 代码落点 | 日志事件 |
|---|---|---|
| ① **没有确认通道** | `capabilities/index.ts:192-208`：`if (!confirmRequester) { …; return false }` | `tool.confirm.unavailable` |
| ② **超时**（缺省 30s，夹在 1s–120s） | `tool-confirm.ts:63` + `:76-80`：`setTimeout` 到点 `pending.delete` + `resolve(false)` | `tool.confirm.timeout` |
| ③ **用户点拒绝** | `resolveToolConfirm(confirmId,false)`（`:100-111`）→ `p.resolve(false)` | `tool.confirm.rejected` |

另外三条同样是"缺省向拒绝"的加固：

- **推送失败也按拒绝**（`tool-confirm.ts:85-91`）—— 逐字理由："推送失败 = 用户根本没看到 ⇒ 必须按拒绝处理（不能'推送失败就默认同意'）"；
- **挂起上限 8 条**（`:58-61`），防 renderer 刷请求把内存撑爆；退出时 `cancelAllConfirms()` **一律按拒绝结算**（`:119-128`）；
- **确认弹窗只能看到 `name + permissionKind + paramsDigest`**（`ToolConfirmRequestSchema`，`shared/src/ipc.ts:931-947`；`paramsDigest` 本身就是哈希）。理由（`tool-confirm.ts:13-15`）逐字："弹窗不需要、也不应该看到参数原文 —— 否则'确认'就变成了把敏感参数又搬到一个可能被截屏的地方。"

**重放保护**：`confirmId` 只接受**当前挂起**的 id（`resolveToolConfirm` 对不存在的 id 返回 `false`，IPC 层只记一条 `tool.confirm.unknown` 日志、**不报错**，因为"可能只是用户点晚了"，`ipc.ts:796-802`）。

**诚实划界**：这三条路径本会话**只到单测/代码层** —— 没有任何真人点过确认弹窗（§5.3）。

### 2.2 `denied` 的工具**从不出现**在模型可见的清单里

- 过滤点：`toolManifestForModel()`（`tool-registry.ts:187-201`），注释逐字：
  "⚠ `denied` 的工具**不进清单**：把模型根本不能用的工具告诉它，只会让它反复尝试并给用户'我做不到'的假象 —— 那正是'模型伪造成功'的温床。"
- 出参投影：`capabilityDiagnostics().modelVisibleTools = b.tools.list().filter(t => t.decision !== 'denied').map(t => t.name)`（`capabilities/index.ts:292`）。
- 运行时读数（**引用** `m3.json` / `kit.json`，§3.3）：12 个工具的 `decisions` **全部 `denied`**，`modelVisible / modelVisibleTools` 都是 **`[]`**。
  也就是说：模型现在能看到**零个**工具。
- 推论（**这是读数，不是猜测**）：**禁止项不可见**这条判据成立的方式是"全部不可见"。
  它同时也说明另一件事 —— **"禁止项不可见"目前没有被单独区分出来**：
  12 个工具一起 denied 时，`modelVisible: []` 既可能是"禁止项被正确过滤"，
  也可能是"所有工具都没授权"。要真正区分，需要至少把 `screen.capture` 的权限打开后重看清单
  （本会话没有做，见 §5.6）。

### 4.1 `stripWakeWord()` 对**含空格的唤醒词**命中却一个字都没剥掉

- **症状**：唤醒词是 `hey airi` 时，`hey airi what is the time` **命中**了唤醒词（`isWake: true`），
  但剥完的正文**还是原句**（一个字符都没少）。
- **根因**：识别文本里的空格位置不可控。早期实现是"跳过标点逐个比字符、同时记录**文本侧**的下标"，
  一旦唤醒词里含空格就**下标错位**。`voice-engine.ts:344-350` 把这次事故逐字记在注释里：

  ```
   * ⚠ 这里踩过一个真实的坑：唤醒词**可能含空格**（`hey airi`），
   *   而识别文本里的空格位置又不可控。早期实现是"跳过标点逐个比字符、
   *   同时记录文本侧的下标"，遇到空格就**错位**了 ——
   *   表现为 `hey airi what is the time` 命中唤醒词却**一个字都没剥掉**。
  ```
- **修法**：把两边都压成**无空白序列**，但**保留每个非空白字符在原文里的下标**，
  匹配成功后用**保存下来的下标**切片（`voice-engine.ts:352-387`）：
  文本侧 `chars[]` + `idxs[]`（`:356-364`），唤醒词侧 `wakeCompact`（`:366`），
  命中后 `text.slice(0,startIdx) + text.slice(endIdx)`（`:383-385`）。
- **我验证到哪一层**：**回归用例实跑通过** ——
  `apps/desktop/test/voice-engine.test.cjs:74-79`
  `★ 自定义唤醒词（英文/带数字）也能剥` 用的正是 `'hey airi what is the time'` / `'hey airi'` → `'what is the time'`。
  另有 `★ 识别插入的标点/空格不影响剥离`（`:29-41`）覆盖 `'你好 助手 今天天气怎么样'` 这种中间插空格的情形。
  **"修之前是红的"我没有复现过**（那要改回源码，超出"只写文档"的边界）。

### 4.2 过宽的 `^AppData$` 目录规则把**每一个**文件访问都拒了（连正常文件都读不了）

- **症状**：加了这条规则之后**所有用例全红** —— 连"白名单内的普通文件可读"这条底线都失败。
- **根因**：临时目录本身就在 `C:\Users\<user>\AppData\Local\Temp\...` 下，
  而 `AppData` **是路径里的一个片段** ⇒ 规则一命中，整条路径被硬拒。
  更根本的问题是**语义也错**：AppData 下面绝大多数是合法的工作数据。
- **修法**：**删掉**一刀切的父目录规则，改为只拒"确实只装敏感东西"的那一层。
  `fs-allowlist.ts:116-131` 把这条教训写成了被引用规则上方的注释，逐字：

  ```
   * ⚠ **不要写 `^AppData$`**。
   *
   * 实测踩到：加了这条之后**所有用例全红** —— 因为临时目录本身就在
   * `C:\Users\<user>\AppData\Local\Temp\...` 下，连"正常的普通文件可读"都被拒了。
   * 更重要的是它**语义上也错**：AppData 下面绝大多数是合法的工作数据
   * （用户完全可能授权 `AppData\Roaming\<app>\data`）；
   * 真正该拒的是**其中的凭据子目录**（下面这几条）。
   *
   * 教训：目录规则的作用域要落在"确实只装敏感东西"的那一层，
   * 一刀切到父目录会把功能一起砍掉（过宽 = 白名单形同虚设，和过松一样是缺陷）。
  ```
- **替代规则**（现在的形态）：`appdata-credentials: /^(Microsoft|Credentials|Protect)$/i`、
  `appdata-browser: /^(Google|Mozilla|Microsoft\\Edge|BraveSoftware|Chromium)$/i`、
  `appdata-tokens: /^(npm-cache|pip|NuGet|gcloud|\.config)$/i`（`fs-allowlist.ts:128-130`）。
- **我验证到哪一层**：**反例集用例实跑通过** ——
  `fs-allowlist.test.cjs:167-177` `★ 过宽的目录规则会被这个反例集抓到（AppData 一刀切就是被它抓出来的）`
  明确把 `Users / AppData / Local / Roaming / Temp / Projects / Documents / src / node_modules / work`
  列为**必须允许**；`fs-allowlist.test.cjs:144-165` 的探针段列表里 `AppData` 也作为**反例**存在。
  这两条用例是**这次修复的看守人**：谁再把父目录一刀切加回来，它们立刻红。
  （"全红"那次现场我**没有亲见** —— 依据是源码注释 + 现在这两条用例的存在与通过。）

### 4.3 "轮不到的死规则"：`dotenv-variant` / `browser-logins` / `aws-credentials`，以及 `System32` 在 `Windows` 后面

- **症状**：没有功能性的 bug，但**审计字段会说谎** —— `PathVerdict.rule` 记的是"实际拦住它的那条"，
  一条永远轮不到的规则会让人以为"是这个规则拦的"，也会误导后来改规则的人。
- **根因**：规则是**按顺序短路**的（`checkPathAccess()` 的 ① 目录循环与 ② 文件循环都是
  `return deny(...)` 立即返回，`fs-allowlist.ts:186-198`）。
  若 A 的匹配集**包含** B 的匹配集，B 永远命中不到 ⇒ **B 是死代码**。
  `System32` 那条的"轮不到"有源码注释逐字为证（`fs-allowlist.ts:93-95`）：

  ```
   * ⚠ 同样是**按顺序短路**：`^Windows$` 会拦住 `C:\Windows\...` 的**每一个**片段比较
   *   （因为 `Windows` 本身是一个路径段），所以 `System32` 那条其实是轮不到的 ——
   *   保留它只会误导。这类"死规则"由单测的穷举用例盯着。
  ```
  `System32` 现在**已不在规则表里**，而是被并进 `windows` 规则的 `why`
  （`fs-allowlist.ts:111`：`why: 'Windows 系统目录（含 System32）'`）。
  文件规则侧的维护要求写在 `fs-allowlist.ts:52-57`：

  ```
   *   ② **不要写被前面规则完全覆盖的规则**。规则是**按顺序短路**的，
   *      一条永远轮不到的规则是死代码 —— 它会让"哪条规则拦住的"（审计字段）
   *      与实际不符，也会误导后来改这里的人。单测里有穷举用例专门盯这件事。

- **修法（能复核的当前形态）**：
  ① 合并 —— `dotenv` 现在是一条 `^\.env(\..+)?$/i`，规则注释写明"一次性覆盖 `.env` / `.env.local` / `.env.production` 等**全部变体**"（`:61-64`），
  所以历史上那条 `dotenv-variant` 已经不存在于规则表里；
  ② 收紧 —— `credential-db` 要求**带扩展名**（`^…\.(json|db|sqlite|sqlite3|kdbx|dat|txt)$`，`:70-75`），
  于是**不带扩展名的裸 `credentials`** 能落到后面的 `aws-credentials`（`:79`）上，不再被前面吞掉；
  ③ 保留并确认可达 —— `browser-logins`（`:81`，`^(key[34]\.db|key[34]\.db-wal)$`）
  排在 `browser-cookies`（`:80`，只匹配 `cookies`/`login data`/`web data`/`cookies-journal`）**之后**，
  两者匹配集不相交。
- **我验证到哪一层**：**当前形态可达 + 穷举用例实跑通过**。
  `fs-allowlist.test.cjs:113-142` `★★ 没有"轮不到"的死规则（死规则会让审计字段与实际不符）`
  用 50 个探针文件名逐个走规则链，断言 `dead === []`；
  `:144-165` `★★ 没有"轮不到"的死目录规则` 同理（探针段里**同时**含 `Windows`、`System32`、

### 4.4 `clipboard.readText()` 是**异步** API，早期按同步写会被 tsc 拦下

- **症状**：若按 `text = clipboard.readText()` 写，运行期拿到的是一个 `[object Promise]` 字符串 ——

   *   早期按同步 API 写（`text = clipboard.readText()`）会被 tsc 拦下 ——

   *   于是"读剪贴板"看起来永远读到一堆无意义内容。异步 API 必须 await。
  ```
- **我验证到哪一层**：**当前形态 + 类型检查层实跑通过** ——

### 4.5 `voice:listen-once` 的**返回形状撞车**：IPC 层的 `ok` 与识别层的 `ok` 是两件事

- **症状**：把 `listenOnce()` 的结果直接展开返回时，**识别失败会把 IPC 的成功标志也压成 `false`** ——
  调用方于是**无法区分**"通道坏了"与"没听清"。
- **根因**：两个 `ok` 语义不同：IPC 的 `ok` 表示**通道跑通**，`r.ok` 表示**识别本身成功**。
  `ipc.ts:755-763` 把这条逐字写下：

  ```
   * ⚠ 顺序：先展开 `r` 再写 `ok:true`。
   *   反过来会让 `r.ok` 覆盖掉 `ok:true` —— 而这里的 `ok` 是 **IPC 层**的成功标志
   *   （通道跑通了），`r.ok` 是**识别本身**的成功标志（听清了没有）。
   *   两者语义不同：识别失败（`r.ok=false`）时，IPC 仍然是成功的，
   *   且必须把 `r.reason` 如实带回。混成一个字段会让调用方无法区分
   *   "通道坏了"与"没听清"（tsc 用一个 TS2783 提醒了这一点）。
  ```

  但**契约与实现在这里是漂移的**，如实记下。

### 4.6 探针把测试目录建在 `userData` 下 ⇒ 被本应用自己的数据目录规则拒掉（**规则是对的，改的是探针**）

- **症状**：探针要"授权一个真实存在的普通目录"来验证白名单，结果 `fsAllowDir` 直接返回失败
  （`code: 'SENSITIVE-DIR'`），看起来像"白名单功能坏了"。
- **根因**：`userData` 就是 `…\AiriMateOne`，而规则表里有一条
  `app-data: { id: 'app-data', segment: /^AiriMateOne$/i, why: '本应用自己的数据目录（含加密密钥文件）' }`
  （`fs-allowlist.ts:110`）—— 这是**硬拒绝**，即使它在白名单里也拒（`:186-192`）。
- **修法**：**改探针，不改规则**。`bootstrap.ts:3790-3798` 逐字：

  ```
   * ⚠ **不能放在 `userData` 下**：那里是 `AiriMateOne`，本身就有一条
   *   "本应用自己的数据目录（含加密密钥文件）"硬拒绝规则 ⇒ 加不进去。
   *   实测就是这样被拒的（`SENSITIVE-DIR`）—— 那是**规则正确工作的证据**，
   *   所以探针改用一个真正中性的临时目录（`os.tmpdir()` 下的探针专属目录）。
  ```
  现在的探针目录是 `join(tmpdir(), `airimate-m3-probe-${process.pid}`)`（`:3798`）。
- **我验证到哪一层**：**引用探针产物 + 代码层** ——
  `m3.json.fsAdd.label = "airimate-m3-probe-13840"`（`ok: true`，即中性临时目录**能**被授权，
  后缀 `13840` 正是当时那个进程的 pid），
  而 `fsAddSensitive.code = "SENSITIVE-DIR"`（加 `userData\.ssh` 被拒）。
  **"第一次用 userData 被拒"那次的现场我没有亲见**，依据是探针里留下的这段注释。

### ⑧ 补齐：排除区**真的涂到像素上了**（M4 阶段回头补的）

原文把这条记成"只算掩码、没有落到像素"，方向是对的，但实际情况还要更糟一层：
`buildRedactionMask()` 的注释里写着"实际涂抹发生在**同一次**处理里（见 `applyMask`）"——
而 **`applyMask` 这个函数在全仓根本不存在**（`grep` 只有那一行注释命中）。
注释在描述一件没实现的事，比没有注释更坏：读代码的人会以为脱敏已经做了。
这正是本工程明确定为缺陷的"注释与实现不一致"。

补法：

| 新增 | 作用 |
| --- | --- |
| `paintMaskOnBitmap(bitmap, size, mask, fill)` | **纯函数**，直接改 BGRA 位图；可被单测机械验证 |
| `applyRedactionToImage(img, mask, nativeImage)` | Electron 胶水层：`toBitmap()` → 涂抹 → `createFromBitmap()` |
| `isPixelFilled(...)` | 断言辅助（越界返回 false，不读越界内存） |

接线：`screen.capture` 在**唯一持有画面的地方**就地涂抹；
涂抹失败 ⇒ **整次截图失败**（`已中止本次截图，不会返回未打码的画面`），
**绝不降级成"照样把没打码的图交出去"**。

出参如实分成两个数 —— 这是本节最要紧的一处：

- `maskedCells` = **计划**打多少格（掩码统计）；
- `maskedPixels` = **真的**涂了多少像素（涂抹读数）。

两者分开报，是为了让"打算做"与"做到了"无法互相冒充。摘要里还加了
`exclusionPainted`（排除区是否真的涂过）与 `sensitiveDetector: 'not-implemented'`
（敏感信息**自动识别**尚未接线）—— 把没做的事写在返回值里，而不是留给读者猜。

**为什么"反正不往外传"也要真涂**：保证必须是**结构性**的。只要画面存在于主进程，
它就应该只以"已按用户排除区打过码"的形态存在 —— 将来任何新增通路
（送模型、落盘排查、预览窗）拿到的那张图**已经**是打过码的，
不需要（也不可能）依赖每个调用方记得自己去涂。

**涂抹过程中发现的真 bug**（由单测抓出，不是靠读代码）：格→像素的映射一开始用
`floor(起点) … ceil(终点)`，本意是"再小的区域也至少覆盖 1 像素"，结果**相邻两格会重叠** ——
`W=40 / grid=16` 时第 0 格是 `[0,3)`、第 1 格是 `[2,5)`，像素 2 被涂了两遍。
单测 `整屏排除 ⇒ painted === 像素总数` 当场变红（**1536 ≠ 960**），
这才暴露"打码像素数"这个读数本身是**虚高**的 —— 一个虚高的安全读数比没有读数更危险。

改成 `floor(起点) … max(起点+1, floor(终点))` 并把栅格夹到不超过像素数后，
在 `grid <= min(W,H)` 时两个性质**同时**成立：每格 ≥ 1 像素，且相邻格首尾相接、不重不漏。
（原来要在"至少一像素"和"不重复计数"之间二选一，是因为映射方式选错了，不是因为真的冲突。）

**为什么把纯逻辑与平台胶水分开**：验收环境跑不到真屏幕（见本节 ⑤），
"能不能涂对"就只能靠纯函数单测来机械证明。`applyRedactionToImage()` 本身
仍属**未实测**代码（它需要一张真实 `NativeImage`），
但它调用的 `paintMaskOnBitmap()` 被下面这些用例完整覆盖：

```
★★ 掩码真的改像素：排除区内的像素被涂成不透明填充色
★  没有排除区 ⇒ 一个像素都不改（painted=0 是"没脱敏"的诚实读数）
★  整屏排除 ⇒ 每个像素都被涂（且 painted === 像素总数，不重不漏）
★  极小的排除区在像素上至少涂 1 个像素
★  位图太小 / 栅格非法 ⇒ 什么都不涂并返回 0（绝不越界写）
★  填充色可配，且 alpha 会被写进去
★★ 掩码格与像素块的映射与 buildRedactionMask 的比例一致（8/16 栅格对得上）
   isPixelFilled 越界一律返回 false（不读越界内存）
```

`apps/desktop/test/computer-use.test.cjs` **25 → 33**；desktop 全量 **356 → 364**。
