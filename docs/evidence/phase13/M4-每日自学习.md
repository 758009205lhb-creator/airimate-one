## 1. 判据逐条（判据 / 证据 / 结论）

### 1.1 每天固定时间执行一次反思任务

```ts
// apps/desktop/src/main/reflection-engine.ts:230
export function reflectionDue(now = new Date()): boolean {
  const s = loadSettings()
  if (!s.selfLearningEnabled) return false          // ← 默认配置下**永远** false
  if (hhmm(now) !== s.selfLearningAt) return false  // ← 到点才跑
  const st = loadEngineState()
  return st.reflectionDay !== localDayKey(now.getTime())  // ← 当天只跑一次
}
```

三个条件缺一不可，且**顺序是刻意的**：开关在最前（默认关闭 ⇒ 后面两个条件根本不会被求值，
不存在"关着还跑了一次"的窗口）。

调用点只有一处（`apps/desktop/src/main/proactive-engine.ts:613`），位于 tick 顺序的
「早安电台之后、定时提醒之前」：

```ts
if (reflectionDue(now)) {
  const r = await runReflection()
  if (r.ran) { ... log().info(..., 'proactive.reflection.ran') }
  else { skipped.push(`reflection:${r.skippedReason ?? 'skip'}`) }
} else { skipped.push('reflection:disabled') }
```

tick 间隔 `TICK_INTERVAL_MS = 10_000`（`proactive-engine.ts:94`），
而 `hhmm()` 的粒度是分钟 ⇒ 目标那一分钟里有约 6 次机会命中，不会因为一次 tick 卡顿而整天漏跑。

**证据**：`apps/desktop/test/reflection.test.cjs`
- `★★ 自动触发严格受开关约束（reflectionDue 是唯一自动入口）`
- `★ 关闭时不会被自动触发（reflectionDue 为 false）`
- `★ 按天去重：同一天第二次不会重复跑（force 例外）`

**结论**：通过（单测 + 代码结构）。**但"跨天真的会自动跑起来"没有实跑过** —— 见 §5。

### 1.2 总结当天对话，提取偏好 / 重要事实 / 待办 / 情绪变化

`EXTRACT_RULES` 共 **17 条**，五类：

| 类别 | 条数 | 规则 id | base 置信度 |
| --- | --- | --- | --- |
| `fact` | 6 | `fact-name` / `fact-birthday` / `fact-live` / `fact-job` / `fact-allergy` / `fact-callme` | 0.85 – 0.92 |
| `preference` | 4 | `pref-like` / `pref-dislike` / `pref-habit` / `pref-favorite` | 0.78 – 0.85 |
| `todo` | 3 | `todo-plan` / `todo-remind` / `todo-deadline` | 0.60 – 0.65 |
| `emotion` | 3 | `emo-tired` / `emo-happy` / `emo-stress` | 0.45 – 0.52 |
| `habit` | 1 | `habit-schedule` | 0.45 |

**分界是刻意的**：身份类事实（名字/生日/过敏）落在 0.85 以上 ⇒ 自动写入；
待办与情绪落在 0.60 以下 ⇒ 一律要用户点头。理由写在代码注释里 ——
"我明天要交周报"未必是长期事实，把它当事实写进长期记忆会污染记忆库。

置信度**不是模型自报**，而是确定性算出来的：

```ts
// reflection-extract.ts:125
export function scoreOf(base: number, hits: number): number {
  const raw = base + 0.05 * Math.max(0, hits - 1)
  ...
}
```

同一件事被说两次 ⇒ 小幅提升（0.05/次，上限 0.97）。**由规则强度决定，与模型无关** ——
模型输出在 M4 里根本不参与置信度判断（`method: 'heuristic'`，如实标注，不谎称用了模型）。

**证据**：
- `★ 置信度由规则强度确定性算出（不是模型自报）`
- `★ 身份事实 = 高置信度；情绪/习惯 = 低置信度（分界是刻意的）`
- `★ 待办类也是低置信度（"我要…"未必是长期事实 ⇒ 必须确认）`
- `★ 只扫用户说的话（她自己的回复不该被当成用户的事实）`
- `★ 同一件事说两次 ⇒ 置信度小幅提升（幅度刻意很小）`
- 探针 `m4.confidence.high-exists` / `m4.confidence.low-exists` 均 **true**，
  实测分布：`high=[{fact, 0.9}]`，`low=[{todo, 0.6}, {emotion, 0.5}]`（`m4.json#confidenceSplit`）

**结论**：通过。

### 1.3 高置信度写入长期记忆；低置信度**必须询问用户**

这是 M4 最要紧的一处语义，实现在 `reflection-engine.ts` 的写入闸门：

| 条件 | `approval` | 是否写记忆 |
| --- | --- | --- |
| `confidence >= 0.75` 且**非** dryRun | `auto` | ✅ 写，并回填 `memoryId` |
| `confidence >= 0.75` 但 dryRun | `pending` | ❌ 不写（演练不许悄悄改记忆） |
| `confidence < 0.75` | `pending` | ❌ 不写 |
| 该文本曾被用户拒绝过 | `skipped` | ❌ 不写、**也不再问** |

探针实测（`docs/evidence/phase13/m4.json`）：

```
dryRun:  items=3  autoWritten=0  pending=3        ← 演练一条都没写
realRun: items=3  auto=1         pending=2        ← 真的跑：只写了那 1 条高置信度
pending: count=2
confirm: memoryId=m_muq735ls_2   memoryDelta=1    ← 用户点头后才写
reject:  memoryId=null           memoryDelta=0    ← 用户拒绝就不写
```

对应 27 条探针判据里的 5 条，全部 `true`：

```
m4.real.auto-wrote-high-confidence
m4.real.auto-items-have-memory-id
m4.real.low-never-auto-written
m4.decide.approve-writes-memory
m4.decide.reject-does-not-write
```

**"拒绝过的结论不再重复提问"** 是刻意加的（`wasRejected()` 指纹表）。原因写在代码注释里：

> 如果每跑一次就把同一件事再问一遍，用户会把"确认"当成骚扰而全部点掉 ——
> 那这条防线就失效了。拒绝是一次有意义的信号，必须被记住。

代价也如实写在注释里：用户"改主意"需要自己主动再说一次。

**结论**：通过（探针 27/27 + 单测）。

## 2. 三条「默认不执行」的语义

### 2.1 默认关闭

```ts

```

`runs: 2` 是探针自己手动 `force` 跑出来的（探针在这一步之前跑过 dryRun 与真跑各一次），
不是自动触发 —— 自动路径在 `enabled:false` 下恒为 false。

### 2.2 拒绝不重复问

见 §1.3。`skipped` 状态在 UI 里的文案是「曾拒绝过，跳过」（`LearningPanel.vue:72`）。

### 2.3 `dryRun` 不写记忆

`runReflection({dryRun:true})` 把 `writeMemory` 强制为 `false`，**连高置信度也不写**，
并如实把它标成 `pending`：

```ts
} else if (high && !writeMemory) {
  // 演练：高置信度也不写，如实标为待确认（不能让 dryRun 悄悄改变记忆）
```

探针 `m4.dryrun.no-memory-write` + `m4.confidence.high-all-pending-in-dryrun` 均 true。
**为什么要有 dryRun**：探针本身不该污染用户的真实记忆库 —— 这是"验收动作不能改变被验收状态"。

## 4. 本阶段修复的真实缺陷

按"发现 → 为什么有害 → 怎么修"记，全部是在**跑起来之后**才暴露的。

### 4.1 `pendingItems()` 的排序**不是全序** ⇒ "第一条"会漂

待确认列表按 `createdAt` 排。同一轮反思里所有条目共用同一个 `started` 时间戳
⇒ `createdAt` 完全相同 ⇒ `Array.prototype.sort` 在相等键上的相对顺序**不保证稳定跨引擎**。
后果：UI 显示的第一条、单测取的第一条、探针取的第一条可能是三条不同的。

修法：加 `kind` → `id` 两级兜底，凑成全序。单测现在会断言"两次调用取到同一条"。

### 4.2 `force` 的语义在**注释与实现之间**不一致

注释写的是一回事，代码是另一回事（`force` 到底绕不绕过用户开关）。
这不是笔误 —— 两处不一致时，下一个读代码的人会按注释去理解，然后写出错的调用方。

修法：先确定语义（**`force` 同时绕过去重与开关**，因为它只由用户显式动作或探针传入；
自动路径走 `reflectionDue()`，严格受开关约束），再把注释改成与实现一致，
并补一条单测把这个语义钉死（`★ force 同时绕过去重与开关`）。
本工程把"注释与实现不一致"当作缺陷处理，本阶段修了两处（另一处见 §4.5）。

### 4.3 规则跨全角逗号捕获 ⇒ `我喜欢抹茶，我喜欢抹茶` 被当成一个偏好

`pref-like` 早期的排除字符集只有 `。！？!?`，**漏了全角逗号**。
用户说"我喜欢抹茶，我喜欢抹茶"（同一句里说了两遍，很常见）时，
捕获组一路吃到句尾，提取出 `抹茶，我喜欢抹茶` 这么一条**拼接出来的假事实**。

修法：所有规则的排除字符集统一补上 `，,`。并在注释里写明原因 ——
否则下一个人加规则时会再犯一次。

### 4.4 `todo-plan` 漏掉"我明天要交周报"

规则早期要求"我"与"要"相邻。中文里时间状语插在中间是**常态**
（"我**明天**要交周报""我**下午**要去开会"），于是最典型的待办句式反而提不出来。

修法：在"我"与"要"之间允许可选的时间词。补了一条测试用例把这个句式固定下来。

### 4.5 `ReflectionStatusSchema` 要求 `pendingReflections`，而 `proactiveStatus()` 没给

主动引擎的状态投影被 `ReflectionStatusSchema` 校验，新增 `pendingReflections`
字段后 `proactiveStatus()` 没同步 ⇒ **zod 解析失败**。这类失败很阴：状态通道整体挂掉，
但表面上看是"提醒功能不好用了"，跟反思八竿子打不着。

修法：`proactiveStatus()` 补上该字段（并在存储坏掉时容错为 0，见
`reflectionDigestSafe()` —— 反思存储坏掉不该让**整条状态通道**失败）。

### 4.6 测试自身的两处假信号

- **活动采样用了 `Date.now()` 而不是注入的固定时钟** ⇒ 单测里"今天的活动统计"
  与注入的 `now` 对不上，读数随机漂移。修法：统一走注入时钟。
- **浮点 `0.05` 增量比较** ⇒ `0.9 + 0.05 === 0.9500000000000001`。
  修法：`scoreOf()` 结果四舍五入到 2 位小数，并在测试里按 2 位比较。

### 4.7 `ui` 探针的 tab 断言在**有徽标**时假失败

真实 tab 是 `提醒1`（未读徽标拼在后面），而断言写的是 `tabs.includes('提醒')`
⇒ 明明功能正常却报 `ui.tab-reminder-exists` 失败（当时读数 42/43）。

修法：改成前缀匹配 `tabs.some(t => t.startsWith(label))`。
修完重测 **43/43**。记这一条是因为**假失败与假通过一样有害**——
它会诱使人去"修"本来没坏的东西。

### 4.8 「保留 400 天」在状态层是**手写的第二个 400**（由 §5 的一次误读翻出来）

`reflection-store.ts` 的裁剪用的是 `KEEP_DAYS`，而 `reflectionStatus()` 里
`keepDays` 是**直接写死的 `400`**。两份独立常量，没有任何东西保证它们相等。

为什么有害：这个数字会显示在界面上。改了裁剪上限却忘了改状态上报，
界面就会继续宣称"保留 400 天"——一个**看起来生效、实际早就不对**的上限，
比没有上限更糟：用户会据此以为旧记录会被自动清掉。

修法：`KEEP_DAYS` 改为 `export`，`reflectionStatus()` 从存储层 import 它，
并补两条单测：

- `★ 保留上限只有一个来源：reflectionStatus().keepDays === KEEP_DAYS`
- `★ 超过保留上限时按天裁剪，保留最新的这几天`（造 403 天，断言裁到 400、
  最新的一天排在最前、最旧的一天不在、且**落盘可读回**——裁剪不是只在内存里）

顺带钉住一条**跨包耦合**：`ReflectionStatusSchema.keepDays` 是 `.max(400)`。
把 `KEEP_DAYS` 调到 400 以上会让状态通道的 zod 校验失败 —— 那会表现为
"提醒/日程整块不好用"，跟反思八竿子打不着，极难定位。
所以单测里直接断言 `KEEP_DAYS <= 400`，让改这个常量的人在**单测**阶段就撞墙。

desktop 单测 **354 → 356**。同一数字只能有一个来源，这一条现在是被机器看着的。

### 4.9 （顺手回头补的 M3 缺口）排除区**从来没被涂到像素上**

M4 期间回头读 `computer-use.ts` 时发现：`buildRedactionMask()` 的注释写着
"实际涂抹发生在**同一次**处理里（见 `applyMask`）"——而 **`applyMask` 全仓不存在**
（`grep` 只有那一行注释命中它）。也就是说"排除区域打码"当时只是一个**说法**：
掩码算出来了、统计数字报出来了，**没有一行代码改过像素**。

这属于本工程明确定为缺陷的"注释与实现不一致"，而且后果是安全性的：
一旦将来有通路把画面交出去，"用户圈出来的排除区"形同虚设。

补的内容见 `docs/evidence/phase12/M3-语音与智能体能力.md` §⑧（含涂抹过程中
由单测抓出的一个真 bug：格→像素映射重叠导致"打码像素数"虚高）。

与 M4 的关系：**这不是 M4 的需求**，是回头补 M3 的账。记在本阶段文档里，
是因为改动确实发生在本阶段，不记就成了"来源不明的改动"。

**仍未实现**：敏感信息**自动识别**（OCR / 识别器）。当前只按用户手工圈定的
排除区打码，未圈出的敏感内容不会被自动盖住 —— 这一点同时写在截图提示文案、
`screen.capture` 摘要（`sensitiveDetector: 'not-implemented'`）与 M3 文档 §⑤ 里。

`apps/desktop/test/computer-use.test.cjs` **25 → 33**；desktop 全量 **356 → 364**。

| 6 | **多显示器 / 跨时区下的 `localDayKey`** | 只在本机时区跑过 | 低：`localDayKey` 走本地时间，跨时区旅行会出现"同一天反思两次"或"漏一天" |

是**两份独立常量**，改一处忘一处就会让界面显示一个**看起来生效、其实早就不对**的上限。
