## 3. 顺带发现的两件事（都必须记下来）

### 3.1 `fps5s` 的衰减形状证明"帧确实停了"

每个受干扰段的 `fps5s` 呈**几何衰减**（16.2 → 6 → 3.7 → 2.7 → 2.1 → 1.7 → … → 0.2）。
这是**滚动窗口**在没有新帧时的特征：分母固定在 5 秒，分子不再增长 ⇒ 值单调下降。
⇒ 读数可信，不是采样 bug。

### 3.2 ⚠ **待机轮换是"帧驱动"而不是"时间驱动"** —— 一个真实的实现特性

分段估计轮换周期：

| 时间窗 | 平均 index 步长 | 反推周期 |
|---|---|---|
| 0–20 min | 2.513 | **11.94 s** ✅ |
| 20–40 min | 1.846 | 16.25 s ❌ |
| 40–60 min | 2.513 | **11.94 s** ✅ |
| 60–80 min | 0.821 | 36.56 s ❌ |
| 80–100 min | 1.769 | 16.96 s ❌ |
| 100–120 min | 2.350 | 12.77 s ✅ |

**周期并没有真的变化** —— 它随"帧率"一起缩放。
原因：`director.tick()` 在**渲染循环里**被调用（`Stage.animate()`），
所以**掉帧会直接拉长待机轮换的墙钟间隔**。

- 空闲时：11.94s（与判据 12s 差 0.5%，落在计时精度内）
- 机器繁忙时：可拉长到 36s

**这是设计取舍，不是缺陷**（桌宠在后台被挤占时"慢一点换动作"比"跳帧"更自然），
但它有**两个必须说清的后果**：
1. 判据 A13「12s 轮换」严格来说只在"渲染循环正常跑"的前提下成立 ——
   既有 A13 探针在一个空闲的窗口里测量，所以它的 12s 是**有效**的；
2. 长稳判据**不能**用"轮换周期"当健康指标 —— 它会被机器负载混淆。
   健康指标应当用**不变量**（`windowCount`/`vrmCount`/`scene` 等）与**堆斜率**，
   这两项在 run2 里全程正常。

## 4. 方法论教训（比结论更重要）

**不能在跑长稳测试的同一台机器上做重活。**

我第一次和第二次都犯了同一个错误：一边跑 2 小时浸泡，一边跑 `npm run typecheck`
与三个测试套件。后果是：

- 第一次：机器**睡眠**（我在轮次之间等待），采样 1.4 小时空洞 ⇒ 不计通过；
- 第二次：机器**被我的测试饿住**，帧率掉到 20 fps 左右 ⇒ A16 不达标。

两次都不是应用的缺陷，但两次都**污染了测量**。所以：

> **run3 期间我保持空闲**（不再跑构建/测试/扫描）。
> 若这仍然不达标，才说明是应用自身的问题。

## 5. 证据不覆盖的修订

同一判据跑多次时，汇总文件**必须按输入文件名派生**
（`A15-soak-run3.jsonl` → `A15-soak-run3-summary.json`），
否则后一次会**覆盖**前一次的证据 —— 而"那一次为什么不算通过"恰恰需要留证
（run1 被睡眠打断、run2 受并发干扰）。

已把 runner 与分析器都改成**从输入文件名派生**，不再硬编码。
