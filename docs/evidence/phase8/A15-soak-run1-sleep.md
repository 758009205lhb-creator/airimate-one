## 2. 逐项判定：哪些是"应用的问题"，哪些是"环境的问题"

**这是本文档最重要的一节** —— 把两类原因分开，否则会把环境问题误记成代码缺陷。

| 观察 | 判定 | 依据 |
|---|---|---|
| 时长 10338s ≥ 7200s | ✅ 达标 | 但达标不等于"连续运行"，见下 |
| 两个采样空洞（3655s / 4912s） | ⚠️ **环境（系统睡眠）**，非应用缺陷 | 空洞后 `fps1s=0`、`fps5s=0`，且 `heap` 反而降到 115 MB —— 这是**进程被挂起**的特征，而不是"渲染卡死"（卡死时 heap 不会下降、不变量会破坏） |
| `fps5s min = 0` | ⚠️ 同上 | 只出现在两个空洞后的样本；其余 **60/62** 个样本 `fps5s ≥ 63.2` |
| `advancing=False` | ⚠️ 同上 | 动画时钟在挂起期间当然不推进；恢复后仍在推进 |
| 不变量违规 2 条 | ⚠️ 都是**采样间隔**违规，不是"多了一个窗口/角色" | 无一条是 `windowCount≠1` / `vrmCount≠1` / `live2dCount≠0` / `scene≠1` |
| **真正有效的连续数据** | **仅前 1772s（≈30 分钟）** | 之后就是睡眠空洞 |
| 30 分钟有效窗口内 | ✅ 全部健康 | 不变量 0 违规、T-pose 0、轮换模式复现 0 错位、fps 62–68、heap 117–155 MB 无增长趋势 |

**⇒ 正确结论**：第一次运行**没有验证到"连续 2 小时"**，
它验证到的是"**连续 ~30 分钟完全健康**"。不能据此写 A15 PASS。

## 3. 根因与修法

**根因**：我在对话轮次之间等待，机器空闲后按电源计划自动睡眠。
证据：两个空洞分别长 61 分钟与 82 分钟，且都在"无用户活动"的时段。

**修法**：新增 `tools/qa/run-soak-and-finish.ps1`，运行期间用 Win32
`SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` 阻止睡眠：

```powershell
[SleepBlock]::Block()      # 进程活着期间生效
try   { ...跑浸泡... }
finally { [SleepBlock]::Release() }   # 无论成败都释放
```

**为什么用 `SetThreadExecutionState` 而不是改电源计划**：
- 它是 **Win32 标准做法**（媒体播放器、下载工具都这么干）；
- 作用域**只在本进程存活期间**，进程退出/被杀后**自动失效** ——
  不会给用户机器留下"永久不休眠"的副作用；
- 改电源计划（`powercfg /change standby-timeout`）会**持久修改用户的系统设置**，
  且本机 `powercfg /requests` 需要管理员权限 ⇒ 改完既不干净也难验证。

## 4. 这次踩坑暴露的**判据设计缺陷**（已修）

我原来的分析器只检查"**总时长** ≥ 7200s"，于是这份数据会得到：
`passDuration = true`（10338 ≥ 7200）—— 看起来"2 小时达标"。

**但"总时长"不等于"连续运行"**：63 秒的采样间隔上限已经能抓到大空洞，
可我此前**没有把"间隔违规"接进 `passA15`**（只当作一条 warning 列出来）。
修法：间隔违规计入 `violations`，而 `passA15` 要求 `violations.Count -eq 0`
（本轮的实现里已经这样接了，所以这次正确地报了 FAIL）。

> 教训：**判据的"通过条件"必须包含"证据质量条件"**。
> 一份"时长够但中间断了 1.4 小时"的数据，绝不能算"连续运行 2 小时"。
